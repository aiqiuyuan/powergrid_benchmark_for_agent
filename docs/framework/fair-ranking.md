# 每个任务如何建立公平排行

**状态：2026-10-14确定比较路线与验收条件；生产任务、强基线和独立终评面板仍待认证。** 本文件落实[《电网算法演化 Benchmark 的原赛可比性与公平排行说明》](https://chatgpt.com/space/page_949f304b2f68819191df113e9be1b7d9)的建议。该Page的访问权限可能与GitHub不同；下文保留独立可读的决定和公开一手来源，不依赖读者能打开Page。

## 1. 三种结果必须分开

| 结果类别 | 含义 | 本仓库允许的声明 |
|---|---|---|
| 官方名次 | 组织方按正式提交及评测流程认可的排名 | 只能引用原赛认可的结果；本地重评不授予官方名次 |
| 历史成绩参照 | 冻结算法在公开历史面板运行，与原始目标表或归档提交比较 | 列出输入、信息权限、硬件、种子、时限、环境与评分差异；不把旧隐藏数据说成现在未触碰 |
| 新Benchmark排行 | 实际纳入的方法均按同一发布协议重新执行和评分 | 结论限于本次认证的方法集合；没有复现的历史方法另列外部参照 |

每条结果写入`claim_scope`，禁止把不同类别放进一个名次列。使用原始题目和checker仅对齐了问题的一部分；输入面板、允许信息、决策空间、求解时间和聚合规则仍须核对。跨任务不能直接平均`J`、风险、经济分数和GBP；采用[研究契约](../benchmark-spec.md)中待校准冻结的家族内映射和家族权重，并保留原指标。

## 2. 两类性能与两层时间

**最终算法性能**比较冻结后的求解器、控制器或预测交易流水线，按相同输入、执行资源、接口、评分器与失败规则重跑。已长期开发的公开求解器、预训练竞赛队模型可以进入这一表，但披露训练及外部信息来源。

**智能体开发性能**比较算法如何在同一初始上下文、基线、开发墙钟`T`、资源、模型、选择政策和受保护反馈预算`n`下产生。研究`n`时只有`n`有意变化；长期人工开发方法和预训练冠军不能直接充当“同T开发”的结果。

`T`包括开发、训练、工具、选择和反馈等待；终评有独立的构建及逐实例执行时限。48小时开发与Code1的600秒求解是两层时间，不能互相替代。本文的原赛数字是**历史协议参照**，不是替本轮Configuration选择值；新实验的`T/n/资源/重复/逐实例时间`均由配置清单另行确定。详见[统一评测协议](../protocol/evaluation-protocol.md)。

## 3. 本次为五个家族选择的路线

| 家族 | 优先路线 | 历史参照怎么保留 | 目前是否可发布公平榜 |
|---|---|---|---|
| [GOC](../task-cards/goc-sc-ac-opf.md) | 公开合成面板、原始SC-AC-OPF与完整Code1/Code2的新统一排行 | 同场景`J`和可核对的合成division结果独立列；不复原工业终赛总榜 | 尚不可。完整输出基础已有；新面板、强基线、统一资源与全故障验收缺失 |
| [UC/SCUC](../task-cards/unit-commitment.md) | 原始PGLib-UC通用求解器排行；派生DC SCUC独立扩展 | UC没有官方原赛榜；仅报告固定版本实例的统一重跑 | 尚不可。MILP与独立validator已有；当前终评仍须改成执行源码，新切分未认证 |
| [RTE](../task-cards/rte-maintenance.md) | 首先冻结算法在原始C+X上按15/90分钟结构重评；另建智能体泛化面板 | 逐实例`F_15/F_90`与原表对照；硬件/种子差异说明；积分只按冻结方法集合重算 | 尚不可。代码、实例、目标表入口存在；准备/启动不等于终评完成，许可与完整运行待验收 |
| [L2RPN](../task-cards/l2rpn-grid-control.md) | 现代锁定环境下，同动作权限、同simulate上限、同资源的新认证排行 | 三支领先方法的旧24周公开重评单独保留；它不是同权限公平榜 | 尚不可。代码/权重与兼容适配已取得；能力合同与新面板未认证 |
| [HEFTCom](../task-cards/heftcom-forecast-trade.md) | 原始0–1800 MWh交易边界、原始结算、逐日因果重放的新排行 | 官方逐日提交归档可重算历史输出；冻结最终模型回跑不代表原赛逐日开发轨迹 | 尚不可。数据和starter已有；必须补因果执行、训练截止审计、结算parity与独立期 |

这五条路线不要求把所有任务重新做成同一种比赛。统一的是实验生命周期、可执行提交和证据链，物理定义、决策时点和合理的任务执行限额由各自Adapter保留。[具体合同](task-adapters.md)规定输入、输出、认证门槛和基线候选。

## 4. GOC：公开合成统一重评

采用原SC-AC-OPF数学定义及官方有效性/可行性、软惩罚语义。Code1生成基态，Code2从同次冻结基态生成全部指定故障响应；不能固定故障响应削弱决策空间，不能从不同候选拼接故障。公开合成集允许复现物理评分；工业实例不公开，因此公开数据无法恢复包含工业实例的原全量终赛。

新排行所有方法在同一发布的网络/场景面板上完整运行。规模分层先报告原始`J`、可行性、故障覆盖与时间，再按发布前冻结的固定参考方法映射聚合；没有确定映射与失败分值前不发布全家族名次。若特设原赛合成历史参照，需要选定Division及原来的网络内/网络间两层聚合，禁止把少数单例`J`直接当成总榜。Performance profile、依赖对手的惩罚不能在不重算受影响方法的情况下插入新算法。[官方数据归档](https://data.openei.org/submissions/6153)、[原赛评分规则](https://data.openei.org/files/6153/Challenge_1_Scoring.pdf)。

基线认证顺序：当前完整数值参考、可行起点，再尝试[gollnlp](https://github.com/gollnlp/gollnlp)。其公开说明指向LLNL原赛提交、旧Ipopt构建与BSD-3许可；源码公开不表示已在本平台构建和重放成功。[LLNL项目说明](https://computing.llnl.gov/projects/gollnlp)。无法运行该强方法时，可先发布实际认证方法的比较，明确不覆盖原赛全部强队。

独立泛化面板按网络来源/场景组审计，已经优化的五个Final场景进入开发或calibration。公开历史面板是事后性能定位；新泛化结论需要开发、selection、反馈和终测各自隔离的组。

## 5. UC与SCUC：标准求解器排行与独立扩展

UC主线保留锁定版本PGLib-UC的原始参数、完整时间窗口和铜板UC定义。冻结源码接受新的实例并独立生成排程；独立validator重算成本和所有原约束。候选报告的solver目标和下界属于诊断，不直接作为权威评分或可信最优性证据。[PGLib-UC固定版本说明](https://github.com/power-grid-lib/pglib-uc/blob/39a7f38cf4703de92f0291f0c873c2e98c789301/README.md)。

完整MILP/HiGHS参考是最低强基线基础；可以纳入不同建模、启发式或求解器，但必须锁定solver许可赛道、线程、资源、预处理和停止条件。未知最优实例报告有效incumbent及可信参考下界，不能把60秒参考解称为最优。用于排名的成本映射、有效率、时间与数值容差须发布前校准，不能因某算法结果改变权重。

派生DC SCUC保留自己的版本、网络/安全行、限额及安全范围；以`track_id=derived-dc-scuc`单列。它不是PGLib-UC的官方赛道，也不声称交流SCUC全物理安全。两例RTS和已有case14/30只用于校准；新实例按系统和日期来源分组，区分同系统时间泛化与跨系统泛化。[UnitCommitment.jl实例与模型](https://anl-ceeesa.github.io/UnitCommitment.jl/0.4/guides/instances/)。

## 6. RTE：C+X历史参照先行

选择原始C+X共30例及15/90分钟结构作为首个历史参照协议。它服务于最终算法定位，与新智能体实验的开发时长无关。原赛Linux、2 CPU、16 GB和种子规则列为对齐目标；若实际平台或种子无法复原，结果标注协议差异，不授予原赛名次。[原赛规则](https://github.com/rte-france/challenge-roadef-2020/blob/master/Challenge_Rules.pdf)、[完整决赛榜与目标表](https://roadef.org/challenge/2020/en/finalresult.php)。

对每实例保留`F_15`、`F_90`、`V=0.8F_15+0.2F_90`、可行性和运行成本。15/90的输出是同一冻结算法、同一发布随机化约定产生的两预算记录；采用连续轨迹快照还是独立执行必须在历史协议核查和认证时固定，不能事后取每项较优结果。新方法与旧目标表的假想积分比较，必须冻结对手集合和可行性规则，按`max(0,10−严格更优方法数)`重算所有受影响方法；不能把新方法与原冠军291积分直接相减。

S34、S56的公开代码是优先强基线候选。各自README声明Gurobi依赖，其中S56还使用OpenMP；许可、版本、进程/线程及预算需认证。商业solver允许赛道与开源赛道分别声明，不能隐藏商业依赖。[S34源码说明](https://github.com/mbmv7/rc)、[S56源码说明](https://github.com/FranciscoParrenoTorres/Roadef2020)。本次没有把已准备或启动的重评认定为完成。

C在赛前公开，X现在也已公开；这一面板不承担“全新未触碰泛化”的声明。算法演化研究另建有暴露审计的四角色面板，原始维护、时段、风险情景完整保留，候选不能把原风险目标替换成CVaR而沿用原赛名义。

## 7. L2RPN：先认证相同能力

旧24个不重复公开周的重评纳入20方法并完成480个episode。其协议让Famou仅使用拓扑/线路动作和每步16、每episode2048次simulate，而三支公开领先方法保留更宽的动作权限和原有搜索预算。旧结果只能说明该不对称合同下的性能定位；其第4等本地名次不能升级为同权限公平榜，也不等于2020隐藏终测榜。上述计数依据本地冻结协议与结果摘要及所引用Page，本次不重新评分。

新主线固定一份现代Grid2Op/LightSim环境合同，对所有方法统一动作类、可见观测/forecast、simulate能力、单步/episode限制、初始化与执行资源。动作与次数的具体值仍待校准，旧375动作与16/2048仅作成本参考。若保留纯拓扑与拓扑加redispatch，两者是独立`track_id`，各自方法均有同一允许权限。公平限制允许上限，不要求每方法实际调用次数相同。

公开领先方法按顺序认证`rl_agent / binbinchen / lujixiang`的源码、权重和训练来源。能力转换如果改变算法，要发布适配差异与新artifact标识；未经限制的原实现另列历史参考。仅做导入、dtype、API兼容且通过回归测试的修改与策略/搜索改变分别记录。模型长期训练成本属于外部预训练信息，不等于在本次T内训练。

新评分保留锁定原生scorer、reference重算与successful-step生存率；不得混用历史重评的成本公式或terminal处理。对终止转移、成本轨迹、seed/backend/reference缓存做parity与独立重放。原2020隐藏24周manifest尚未核验取得；新公开/隔离面板不恢复该身份。[组织方回顾](https://proceedings.mlr.press/v133/marot21a/marot21a.pdf)、[锁定现代原生scorer](https://github.com/Grid2op/grid2op/blob/v1.12.5/grid2op/utils/l2rpn_2020_scores.py)。

## 8. HEFTCom：逐日因果重放

主线选择**测试前冻结算法与训练产物，按市场日逐日重放**，保留原赛交易`0≤bid≤1800 MWh`和结算逻辑。请求只含截止前可得的天气、历史和允许的价格信息；实际次日发电、日前/偏差最终结算价只存在评测端。原赛报价截止为D−1 09:20 UTC，该时点是因果语义的一部分。每项特征需有`issue_time / available_at / target_timestamp`，不能只凭目标日期筛选。[原赛Documentation v4.0](https://zenodo.org/records/13950764/files/Competition%20Documentation%20v4.0.pdf?download=1)、[组织方回顾](https://arxiv.org/html/2507.01579v2)。

主线允许读取已公布的合法历史观测作为特征，但不在终测期间重新拟合权重。若研究滚动重训，另立协议，在预先声明的频率、训练窗口、标签公布滞后及计算预算下，由可信replay控制器逐日开放已公布历史；冻结的是训练配方与更新策略。最终榜反馈和当前/未来标签始终不可用于选择算法。测试阶段允许的在线训练是该扩展的算法行为，不能悄然加入固定权重主线。

Trading以累计GBP为主，保留每半小时收益与风险；Forecasting如启用必须输出九分位并计算pinball；Combined只有两部分都验收后才计算名次组合。原Trading收益按每半小时核算：`bid×DA_price+(generation−bid)×SS_price−0.07×(generation−bid)²`，各物理量、UTC/DST、半小时编号、缺交填补、数据修订和特殊日必须与锁定组织方复算程序对齐。报价文件只是执行结果，不能替代预测交易代码。

归档团队的逐日forecast/trade用于checker校准和历史参照，不是可运行算法基线。[组织方复算代码](https://github.com/jbrowell/HEFTcom24-Analysis)与[归档数据](https://zenodo.org/records/13950764)用于建立parity。GEB公开发布包包含源码与预训练产物，可作为较强基线候选；先审计训练截止、未来信息和依赖，再按新协议重训或纳入符合截止的权重。不能把回溯最终模型的分数称为原赛每日提交成绩。[GEB发布包v1.3](https://github.com/BigdogManLuo/HEFTcom24/releases/tag/v1.3)。

## 9. 排行发布的共同准入门槛

1. `protocol_id/task_version/track_id/split_id`及物理、信息、能力、失败合同冻结；配置占位值全部填实，生产Adapter认证通过。
2. 直接执行冻结算法，在新输入产生输出；源码、依赖、权重、输入、checker、原始结果与artifact哈希可追溯。
3. 每个纳入方法完成同平台认证，包括基线；缺失的强方法显示未覆盖，不能以其归档成绩代替同条件重跑。
4. 独立最终面板完成暴露及组审计，选择/反馈/终测不重合；公开历史参照则准确声明公开性，不额外声称泛化。
5. 准备、工具、T、反馈预算、选择、冻结、终评、错误恢复和结果提交均由[统一生命周期](architecture.md)记录，基础设施失败不伪装算法零分。
6. 排行锁定方法集合、聚合、失败规则、tie-break和统计；开发随机重复与episode/实例重复分开，保留失败和不确定性。新协议变更后生成新表，不混合旧版分数。

当前五个Adapter声明均为`status=design / certification_status=pending / release_ready=false`。本次构建完成可审查的接口与准入门槛；没有新增正式物理评测、没有宣称生产任务已部署或公平榜已生成。
