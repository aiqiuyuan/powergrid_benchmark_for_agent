# 每个任务如何建立公平排行

**状态：2026-10-15。用户已确定五task、n=0／1／3／5／10、每档3次独立开发、T=43200秒及累计token不限；模型、资源、面板和大部分算法执行限额仍待核对／校准，尚无正式公平榜。** 本文件落实[《电网算法演化 Benchmark 的原赛可比性与公平排行说明》](https://chatgpt.com/space/page_949f304b2f68819191df113e9be1b7d9)的建议。该Page的访问权限可能与GitHub不同；下文保留独立可读的决定和公开一手来源，不依赖读者能打开Page。

当前个人侧直接复用`eval-in-loop`，建设重点是task。本文列出**比较需要决定什么、已有哪项约定、决定会影响哪部分task**，供后续逐项填实；它不是新的配置系统，也不要求把五任务迁到独立参考内核、统一JSON ABI或生产服务。已有task入口、原生配置及结果文件能够满足的部分直接复用。范围以[精简设计决定](../decisions/0004-minimal-local-testing.md)为准。

阅读顺序：§1–2确定比较对象和通用设置，§3确定五条路线，§4–8补各task特殊设置，§9区分小测与正式比较条件，§10–11说明如何据此确定最小实现。原赛规则、已做实验的参数与本轮待定值分别记录，不能互相代填。

本轮逐题处理决定、参数依据和实际剩余差额见[原题对齐与参数校准协议](../protocol/task-alignment-and-calibration.md)。该协议已落实用户确认的L2RPN完整原赛动作主线；规范确定不代表task代码修改、同条件基线重跑或成本校准已经完成。

## 1. 三种结果必须分开

| 结果类别 | 含义 | 本仓库允许的声明 |
|---|---|---|
| 官方名次 | 组织方按正式提交及评测流程认可的排名 | 只能引用原赛认可的结果；本地重评不授予官方名次 |
| 历史成绩参照 | 冻结算法在公开历史面板运行，与原始目标表或归档提交比较 | 列出输入、信息权限、硬件、种子、时限、环境与评分差异；不把旧隐藏数据说成现在未触碰 |
| 新Benchmark排行 | 实际纳入的方法均按同一发布协议重新执行和评分 | 结论限于本次认证的方法集合；没有复现的历史方法另列外部参照 |

每条结果记录`claim_scope`，禁止把不同类别放进一个名次列。使用原始题目和checker仅对齐了问题的一部分；输入面板、允许信息、决策空间、求解时间和聚合规则仍须核对。个人小测可先按task报告原始指标，不必先定义跨任务总分。若发布跨任务排行，再冻结[研究契约](../benchmark-spec.md)中的家族内映射和家族权重；不能直接平均`J`、风险、经济分数和GBP。

## 2. 两类性能与两层时间

**最终算法性能**比较冻结后的求解器、控制器或预测交易流水线，按相同输入、执行资源、接口、评分器与失败规则重跑。已长期开发的公开求解器、预训练竞赛队模型可以进入这一表，但披露训练及外部信息来源。

**智能体开发性能**比较算法如何在同一初始上下文、基线、开发墙钟`T`、资源、模型、选择政策和受保护反馈预算`n`下产生。研究`n`时只有`n`有意变化；长期人工开发方法和预训练冠军不能直接充当“同T开发”的结果。

`T`包括开发、训练、工具、选择和反馈等待；终评有独立的构建及逐实例执行时限。本轮12小时开发与Code1的600秒求解是两层时间，不能互相替代。`T/n/重复/token`采用用户已定研究设计；资源与多数逐实例限额需实测后冻结。GOC首个执行档采用有原始来源的Real-Time时限600秒／2K秒，不能把它解释成原硬件复现。详见[统一评测协议](../protocol/evaluation-protocol.md)及[本轮参数依据](../protocol/task-alignment-and-calibration.md#2-四类取值依据与本轮已定设置)。

### 2.1 如何填写设置

以下表格是设置清单，不表示本轮已选择所有值。后续每个task按§10记录“已有事实／本轮选择／状态与依据／实现影响”。状态统一使用：

| 状态 | 含义 |
|---|---|
| 已约定 | 现有研究协议或用户范围决定已明确的政策；仍须核对实际入口是否做到 |
| 建议待确认 | 有优先方案，但尚未作为本轮比较合同冻结 |
| 待数据核对 | 需要检查实际文件、来源、暴露、许可、时间或基线，不能凭文档推定具备 |
| 待校准 | 数值需要先用开发／校准数据测成本、难度或方差，再在正式比较前确定 |
| 不适用 | 当前比较不需要，必须写明原因；例如只比较最终算法时没有共同开发模型要求 |

“原赛规定为某值”“某次预实验用了某值”属于已有事实，不能直接标成“本轮已约定”。小测允许待定项，但必须标为`calibration`或说明协议变体；正式比较仅要求**本次声明适用的项**全部明确，不要求填满独立参考实现的49字段。

### 2.5 开发配置、反馈与两层资源

下列开发项适用于agent开发比较；只比较冻结算法时可标不适用。本轮采用用户已定的**T=43200秒、n=0／1／3／5／10、每task每n独立开发3次、无累计token cap及无累计token预留截断**，共75个run；不把这些研究投入称为原赛规定或统计最优值。模型、CPU/GPU、内存、并发、单例执行预算等仍待核对／校准。多agent的共同T、资源和n按整个run计算，不随agent数量增加配额。

| 编号／设置 | 必须写清楚什么 | 当前政策或待办 | 对task和比较的影响 |
|---|---|---|---|
| C19 初始材料与agent方法 | 任务说明、starter、示例、可见数据、依赖、工具、组织方式及演化策略版本 | 对非研究变量保持一致；具体快照待填 | 对比组织／演化设计时记录有意差异，不能额外给某方法答案 |
| C20 模型与调用参数 | 模型／provider／版本、客户端、采样、上下文、单次输出上限、工具及调用失败策略 | 具体值待确认；无累计token cap、无token预留为已有政策 | 单次响应上限与累计预算分开，记录实际模型成本 |
| C21 开发墙钟T | 起点、终点、编译／训练／公开自测／选择／反馈等待／故障等待如何计时 | 本轮T=43200秒共同上限；上述开发活动计入T，共同准备和冻结后终评另计 | 防止排队、重启或最后训练让某方法获得额外开发时间；实际提前结束如实记录 |
| C22 n与零反馈模式 | n的试验档位、最大受理数、哪些渠道不属于保护反馈 | 本轮n=0／1／3／5／10；n为受保护评测作业上限，原生n=0使用terminal模式 | 不能把judge内部0=unlimited直接当零反馈；公开自测仍计T；受理数不保证完成／投递数 |
| C23 一个反馈作业的内容 | 每作业覆盖哪些实例／episode／天、顺序、种子、是否固定或按预注册方案轮换 | 面板、数量、粒度待定；同task不同n保持相同作业定义 | n=1必须有确定的信息量与成本，不能随候选换较有利成员 |
| C24 反馈可见内容 | 返回字段、聚合、精度、诊断／日志长度、逐例信息、错误信息 | 不泄露私有标签／原始面板；具体schema待确认 | 相同n但反馈精度或逐例结果不同也属于不同协议 |
| C25 受理、并行与截止 | 受理时点、串／并行、在途数量、计数、超额、迟到反馈、投递记录 | 主协议串行受理、候选失败占n、原样基础设施重试不另占n、截止后不供开发已约定 | 先核对原生模式能证明哪些规则；缺项用后端已有能力或标协议变体 |
| C26 开发资源与成本 | 整个run CPU/GPU型号及总配额、内存、磁盘、并发、训练和工具子进程 | 数值及共享／独占方式待校准；所有agent合计 | 实际任务是否能装载、训练、搜索取决于此，非仅模型速度 |
| C27 算法执行资源与时限 | checker资源与候选资源；构建、加载、逐例／阶段／步／episode／日、整批时限及输出落盘 | GOC先采用有来源的Real-Time阶段档600秒／2K秒；其余数值、冷／热启动和超限规则待校准，与开发T独立 | 用task原生执行限额；GOC两个阶段、L2RPN单步等不能仅用一个总timeout替代 |
| C28 准备与复用成本 | 允许提前装依赖／预编译／下载什么；权重训练、候选专用预处理或reference生成算在哪 | 共同无搜索准备可在T前；候选学习及专用搜索不得藏入准备 | 明确缓存与构建边界，避免将算法预计算当免费公共资源 |

不同task的一次反馈成本及信息量可以不同，必须报告；相同n只表示本协议的作业次数，不能自动解释为跨task等信息或等算力。

| 资源和状态 | 冻结控制器默认无运行期LLM；episode间重置 | 初始化／模型加载／每步／整episode预算、CPU/GPU／内存、搜索及训练资源 | 防止预训练、在线训练与纯推理隐性混合 |

## 8. HEFTCom：逐日因果重放

主线选择**测试前冻结算法与训练产物，按市场日逐日重放**，保留原赛交易`0≤bid≤1800 MWh`和结算逻辑。请求只含截止前可得的天气、历史和允许的价格信息；实际次日发电、日前/偏差最终结算价只存在评测端。原赛报价截止为D−1 09:20 UTC，该时点是因果语义的一部分。每项特征需有`issue_time / available_at / target_timestamp`，不能只凭目标日期筛选。[原赛Documentation v4.0](https://zenodo.org/records/13950764/files/Competition%20Documentation%20v4.0.pdf?download=1)、[组织方回顾](https://arxiv.org/html/2507.01579v2)。

**市场日必须恢复为英国本地23:00至次日23:00，时间戳是半小时起点。** 夏令时切换日不能强求48行，例如2024-03-31只有46个period。旧UTC自然日切分及48行过滤需要修正，旧天数不能直接冻结；报价越界应拒绝，不能用静默clip修饰结果。保留现有DWD聚合天气作为明确的本地信息变体，全部基线按同输入执行；它不等同于原赛完整DWD＋GFS格点及额外合法信息。固定权重也属于本地实验政策，原实时竞赛允许更新。实际正式市场日2024-02-20至05-19的发电／价格标签本地尚缺，须取得并对账后才可作为新终评。详见[本轮HEFTCom决定](../protocol/task-alignment-and-calibration.md#8-heftcom原交易语义恢复信息和训练变体说清楚)。

主线允许读取已公布的合法历史观测作为特征，但不在终测期间重新拟合权重。若研究滚动重训，另立协议，在预先声明的频率、训练窗口、标签公布滞后及计算预算下，由可信replay控制器逐日开放已公布历史；冻结的是训练配方与更新策略。最终榜反馈和当前/未来标签始终不可用于选择算法。测试阶段允许的在线训练是该扩展的算法行为，不能悄然加入固定权重主线。

Trading以累计GBP为主，保留每半小时收益与风险；Forecasting如启用必须输出九分位并计算pinball；Combined只有两部分都验收后才计算名次组合。原Trading收益按每半小时核算：`bid×DA_price+(generation−bid)×SS_price−0.07×(generation−bid)²`，各物理量、UTC/DST、半小时编号、缺交填补、数据修订和特殊日必须与锁定组织方复算程序对齐。报价文件只是执行结果，不能替代预测交易代码。

归档团队的逐日forecast/trade用于checker校准和历史参照，不是可运行算法基线。[组织方复算代码](https://github.com/jbrowell/HEFTcom24-Analysis)与[归档数据](https://zenodo.org/records/13950764)用于建立parity。GEB公开发布包包含源码与预训练产物，可作为较强基线候选；先审计训练截止、未来信息和依赖，再按新协议重训或纳入符合截止的权重。不能把回溯最终模型的分数称为原赛每日提交成绩。[GEB发布包v1.3](https://github.com/BigdogManLuo/HEFTcom24/releases/tag/v1.3)。

## 9. 排行发布的共同准入门槛

个人校准小测的最少条件是：**填实本次实际运行设置、列明成员、现有baseline能运行并独立评分、候选能生成输出、保存原始结果和失败**。可以先用已暴露的小面板校准成本；尚未满足正式协议的项目明确标为`calibration`／协议变体。无需先实现全部生产保障、并发矩阵、独立参考内核或强队复现。

正式公平比较在上述基础上，完成与声明相符的检查：

1. 本次适用的物理、信息、权限、预算、失败和统计设置已填实，关联明确版本／成员清单；不是仅存在模板或设计声明。
2. 在声明资源下执行冻结算法产生新输出，独立checker对账通过；源码、依赖、权重、输入、评分器和原始结果可追溯。同条件简单基线先跑通。
3. 所有纳入排行的方法按同一合同重跑，包括实际纳入的基线；缺失强方法列为未覆盖，不用其归档成绩替代重跑。
4. 声称独立泛化时，最终面板完成分组和暴露核对，selection／feedback／final成员分开；历史参照准确声明公开性及硬件等差异。
5. agent比较可核对实际T、受理／完成／投递的n、选择和冻结；仅比较最终算法则核对算法执行合同。采用原生记录即可，基础设施失败不伪装算法零分，无法证明的保证不写成已实现。
6. 方法集合、聚合、失败、并列、重复和统计事前固定，保留所有计划run及缺失；只测一次不能宣称稳定提升。变更协议后生成新表。

五个公开Adapter声明仍是`design / pending / release_ready=false`；它们是历史设计记录，不自动代表已有内部task不可小测，也不能证明正式榜已就绪。[RTE canary证据](../completion-step3-cluster-20261015.md)仅支持其实际覆盖范围。本轮只补设置与实现依据，没有运行新实验或改任务代码。

## 10. 每个task怎样把设置落实为实现

下一步每个task先填一份简短记录，可放在已有任务说明／任务卡增补中，不要求新增机器schema。统一使用下表，避免把“事实”“选择”“代码能力”混为一谈：

| 项目 | 已有事实与依据 | 本轮选择 | 状态／未决原因 | 对现有task的影响 |
|---|---|---|---|---|
| 用途、版本与声明 | 原赛／数据源、历史实验、现有代码 | 校准／历史／新比较；算法／agent | 按§2.1填写 | 哪些项适用，哪些有理由不适用 |
| 数据与信息 | 真实文件／日期、暴露、可用时点、许可 | 成员、四角色、允许信息／拟合 | 按§2.1填写 | 保留读取方式或补输入筛选 |
| 算法和评分 | 现有入口、输出、checker、baseline | 冻结哪些文件、权限／状态／指标 | 按§2.1填写 | 复用或只补源码执行／独立复算 |
| 预算和反馈 | 现有运行配置及成本；用户已定T/n/token／重复 | T=43200秒、n五档、各3次；其余资源／算法时限／单作业内容填实 | 已定设计不再待确认；剩余工程值待校准 | 使用原生配置，核对实际计时和反馈 |
| 选择和报告 | 现有选模方式、逐例记录、失败 | selection、并列、失败、聚合、重复 | 按§2.1填写 | 不符合原合同则先标变体，必要时最小修补 |

工作顺序：

1. **先定语义和范围。** 确定比较对象、物理问题、信息权限、主指标、数据角色和算法提交要求；列出待核对及待校准项。
2. **用已有task和baseline做校准。** 检查实际文件、入口、评分与成本，允许小预算／小面板；这一步不要求先完成五个新Adapter。
3. **补测剩余数值并冻结本次合同。** 沿用用户已定T/n/token／3次独立开发，按成本／难度填剩余执行预算、成员、容差和失败政策；另定统计方案，不把3次称为充分功效证明。个人小测可明确标定为校准，正式比较前固定适用项。
4. **只实现必要差额。** 对照现有能力逐项标“直接复用／仅配置／最小task修改／本轮不适用”；已有后端能提供的能力直接使用。
5. **验证算法而不是只验证答案。** 在声明输入上运行冻结源码，独立评分并保存记录，再扩到批次。设置变化先更新比较合同，避免看结果后改规则。

task交付给框架的目录格式和算法产物是两件事：前者负责让框架启动并评测问题，后者由agent在开发期产生、冻结后执行。[原生task包说明](native-task-package.md)已按当前`eval-in-loop`源码核对目录、task.toml、artifacts、评分入口与两侧数据边界；不要从旧Adapter设计中的JSON示例反推原生格式。
