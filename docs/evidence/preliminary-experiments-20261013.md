## 3. 按任务族整理的结果

### 3.1 GOC：同一任务族的规模变体

任务要求构造基态与指定故障状态，原始目标 J 越低越好。正式结果的 valid/feasible 与故障覆盖需要同时保留；“可行”不等于所有软罚项为零。预实验只覆盖少量固定场景，不是跨网络泛化测试。[E01–E05](source-index.md#内部证据摘要索引)

| 规模 | 公开场景标识 | 故障数 | 三次最终 J（r1 / r2 / r3） |
|---|---|---:|---|
| 500 母线 | Network_02R-173 / scenario_67 | 693 | 298,666.511910 / 299,543.080924 / 297,568.566878 |
| 2000 母线 | Network_06R-124 / scenario_25 | 2,421 | 996,058.834804 / 994,096.286405 / 988,323.296509 |
| 2312 母线 | Network_70R-422 / scenario_21 | 982 | 373,758.650134 / 373,871.523532 / 373,982.705688 |

以上九次最终结果均有效、可行并完整覆盖指定故障集。实际开发时长明显短于 48 小时：GOC500 为 42.06–79.72 分钟；GOC2000 为 1.33–8.12 小时。GOC2312 的 r2 是有来源关系的修复补跑，不应写成原作业无故障完成。

GOC793 使用 Network_03R-200 / scenario_195（793 母线、86 故障）。均值及“±”为有效分数的均值与样本标准差：

| 最大 n | 有正式分数 | 最终 J：均值 ± 标准差 | 实际计入额度的评测数（r1 / r2 / r3） |
|---:|---:|---:|---|
| 0 | 3/3 | 203,823.242399 ± 3,524.016248 | 0 / 0 / 0 |
| 1 | 3/3 | 201,787.868551 ± 1.080524 | 1 / 1 / 1 |
| 3 | 3/3 | 201,787.696113 ± 0.891206 | 3 / 3 / 3 |
| 5 | 2/3 | 201,791.434421 ± 6.042264 | 失败 / 5 / 5 |
| 20 | 3/3 | 201,782.241176 ± 9.459820 | 17 / 15 / 20 |

这些计数不是“已送达反馈”的完整审计。已有轨迹显示部分运行取得官方 evaluator 源码并构建全量本地估分器，因此配置 n 不能单独代表可用评分信息量。**公开评分公式或公共 checker 的使用本身不是泄漏。**关键问题是：原评测面板是否可见、候选是否能在本地得到等价的全量反馈，以及是否违反明确的信息访问合同。旧协议没有足够强的信息边界；需要逐轨迹审计，不能把所有下载行为都称为作弊。n=20 也尚未完成同等深度审计。[E02](source-index.md#内部证据摘要索引)

GOC30000 使用 Network_30R-048 / scenario_15（30,000 母线、10,810 故障）。新批唯一正式成功为 n0-r1，J=18,781,410.908892。另一个失败运行的中间评测曾得到 J=1,227,102.861438，但模型未收到结果且没有独立终评，不能升格为正式成功。旧历史运行 J=1,132,711.252072 属于另一批校准证据。该规模暂用于压力与恢复测试，常规 benchmark 的数据面板尚需认证。[E05](source-index.md#内部证据摘要索引)

### 3.2 L2RPN：区分小划分与正式主比较

小划分为 train 6 周、feedback 3 周、test 3 周，15 次最终结果有效，正 n 运行合计用满 87 次反馈额度。得分越高越好：[E07](source-index.md#内部证据摘要索引)

| n | 留出 test 均分 ± 标准差（3 次开发） |
|---:|---:|
| 0 | 33.6093 ± 1.4833 |
| 1 | 44.2411 ± 10.1360 |
| 3 | 31.3634 ± 13.7497 |
| 5 | 32.5685 ± 3.4689 |
| 20 | 33.9697 ± 0.0004 |

n=1 的实际开发均时约 9.36 小时，n=5 约 1.20 小时。固定三周测试与三次开发不足以分离反馈作用、开发时长与策略随机性；这些分数也不能换算历史竞赛名次。

正式主比较采用 train/select/feedback/test = 144/48/24/96 周，本批 n=0。LLM 开发、ES、PPO 各五次；PPO+Search 复用对应 PPO 权重，共 15 次开发与 20 份策略。当前仅有 **48 周公开 select** 分数：[E08](source-index.md#内部证据摘要索引)

| 方法 | 公开 select 均分 ± 标准差 | 最终 test |
|---|---:|---|
| LLM 代码演化 | 27.5793 ± 7.1924 | 未执行 |
| ES | 31.5072 ± 0.6869 | 未执行 |
| PPO | 6.6740 ± 1.3500 | 未执行 |
| PPO+Search | 8.2637 ± 4.0365 | 未执行 |

五次 LLM 开发全部因当时 1,600 万累计 token 守卫停止，实际开发 1.58–4.70 小时；ES/PPO 为约 11.92–11.99 小时。因此这批不能声称各方法均获得完整 12 小时。PPO 的低分需要诊断，现有数据不证明实现有 bug；公开选模成绩也不决定最终 test 胜负。

### 3.3 RTE：最明确的任务打包失败案例

公开开发实例 A_07/A_09，反馈和终评均为 A_08/A_12；每例 60 秒求解。原 n=0/1/3 各一次终评 reward 为 0.373050868、0.373261818、0.373271258，starter 为 0.373030004。只有一次重复、面板重合和小幅变化，不能支持方法优劣结论。[E09](source-index.md#内部证据摘要索引)

新增包遗漏三份必需嵌套清单，造成反馈及终评无效。已列文件的哈希一致只验证“列出的文件未变”，没有验证“所有必需文件都在包内”。反馈缺文件发生在环境迁移之前，因此迁移不能解释全部故障。另有模型接口通用 HTTP400，有限重试已准备，上游原因仍未确定。

截至快照：修复包通过文件校验并提交了无模型验收；真实模型工具往返、反馈与终评的完整验收、旧产物补评、替代正式重复尚未完成。补评可以救回候选的算法结果，不能恢复缺失反馈对开发过程的影响，也不是原运行的因果重复。

### 3.4 HEFTCom：时间序列回测与反馈送达

历史划分为 2020-09 至 2022-12 train、2023-01 至 2023-06 public validation、2023-07 至 2024-02 protected scoring，保护评分期共 9,648 个半小时。正 n 的反馈与终评使用同一时期；收入属于对该历史面板的自适应回测，不是 untouched test 或官方比赛排名。[E10](source-index.md#内部证据摘要索引)

| 条件 | 最终平均收入（GBP / 半小时） | 计入额度 / 已取回反馈 |
|---|---:|---:|
| 接口先导 | 25,814.11 | 0 / 0 |
| n=0 | 26,174.26 | 0 / 0 |
| n=1 | 26,166.82 | 1 / 1 |
| n=3 | 26,209.57 | 2 / 1 |
| n=5 | 26,289.66 | 2 / 1 |

每个条件仅一次。n=0/3/5 实际开发 4.87/8.90/4.54 分钟，因当时 100 万累计 token 预算的下一请求预留停止，没有获得完整 30 分钟。n=3/5 的配置额度、计入额度与模型实际取回的信息明显不同。该任务去除累计 token 限制的新版已通过本地检查，但截至快照尚未提交新演化，也未完成全容器验收。

现有 grader 解析归档报价文件并计算收益，没有执行候选特征、预测与交易代码。报价有效可以支持这份静态结果的回测成绩，不能单独证明归档算法可在留出时期重新生成报价；与 UC/SCUC 一样，需要迁移到冻结算法执行合同。

### 3.5 UC / SCUC：有效排程与可泛化算法是两种验收

UC 使用两个完整 48 小时 RTS 实例；SCUC 为两个人工适配的 36 小时 DC 线路安全任务。SCUC 仅涵盖非孤岛线路故障，不涵盖发电机故障、孤岛、AC 无功或完整 N−1 场景；不能冒称官方完整 SCUC benchmark。[E11](source-index.md#内部证据摘要索引)

| 条件 | UC 平均相对成本（越低越好） | UC 计入 / 取回 | SCUC 平均相对成本 | SCUC 计入 / 取回 |
|---|---:|---:|---:|---:|
| n=0 | 1.000000000 | 0 / 0 | 1.000000000 | 0 / 0 |
| n=1 | 1.000000000 | 0 / 0 | 0.999999897 | 0 / 0 |
| n=3 | 0.994570407 | 0 / 0 | 0.999999892 | 1 / 1 |

六份最终排程都通过独立可行性和成本检查，但 grader 解析静态排程，没有重放候选求解代码。全部输入及本地成本检查可见，所以 n 目前只是服务调用上限，不能代表被限制的信息。六次开发均因当时累计 token 守卫停止，实际开发 3.13–11.65 分钟。UC n=3 的面板平均相对改善为 0.5430%；SCUC 约 10⁻⁷ 的变化需要按数值容差处理，尚无实质提升证据。

### 3.6 AHC024：保留为基础设施测试

六次评分全部完成，两份程序各在一个私有用例超时，按既定合同总分为 0；零分不能删除后重新平均。候选的内部时间余量、可行解回退与最坏输入测试需要改进，评测器的 2 秒规则保持原样。该任务不属于五个能源任务族，适合验证超时、失败分类和批次报告。[E06](source-index.md#内部证据摘要索引)

## 5. 这些证据如何约束目标协议

| 预实验观察 | 目标合同必须明确的内容 | 防止形成的错误结论 |
|---|---|---|
| RTE 清单内哈希通过，但缺必需文件 | 完整依赖清单 + 干净环境执行；task 认证先于正式实验 | “有哈希就等于可复现” |
| 多组早于墙钟上限停止 | 新版本只按已声明的开发墙钟计时；不设累计 token cap，保留实际用量与单响应限制 | 把旧短运行视作获得完整开发时长 |
| 评测占槽位而结果未取回 | submitted、completed、delivered 三个阶段，分别记候选哈希、时间和终态 | 将配置 n 当作实际反馈量 |
| public 输入与本地目标可见 | 公开 checker 允许；protected feedback 的实例与结果访问受控 | 将服务调用限制误写成信息限制 |
| 反馈集与终评集重合 | public development、public selection、protected feedback、final test 四种角色 | 把自适应面板优化当作 untouched 泛化 |
| UC/SCUC 只解析已有排程；HEFTCom 只解析已有报价 | 最终测试执行冻结算法，再独立验证输出 | 静态答案通过即宣称算法泛化 |
| SCUC 变化处于数值下限 | 固定容差，报告可行性与实质改善阈值，重新校准难度 | 将 10⁻⁷ 变化解释为演化优势 |
| 补跑、故障与中间高分混杂 | 保留 slot、attempt、恢复来源；区分基础设施失败与候选合法零分 | 用中间高分替代失败，或静默删除零分 |

这些是待实现及验收的目标要求。旧运行保留真实冻结设置，不能事后改写为新协议。已有面板用于校准；后续正式研究应使用新版本、独立重复和另外冻结的 final test。
