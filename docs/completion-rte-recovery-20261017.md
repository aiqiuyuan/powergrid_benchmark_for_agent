## 磁盘与内存处理

提交层增加临时磁盘预留128 GiB、上限256 GiB、Docker临时卷上限224 GiB，排除已知故障节点，并保留原批次强制节点反亲和。加载镜像前检查实际可用空间至少达到预留值。校准已构建两类镜像，实测Docker占用47,257,112,576字节，约44 GiB；这不是12小时磁盘峰值测量，后续仍需观察运行状态。

校准容器内实际cgroup限制已核对：开发2 CPU / 32 GiB、评分15 CPU / 256 GiB。外层21 CPU / 296 GiB配置已由集群API核实；外层cgroup不可读，因此不声称完成了外层cgroup实测。

开发内存限制维持32 GiB。修订的是原先“一旦出现OOM就拒绝终评”的审计口径：若事件仅发生在开发容器，原生开发已正常截止、完整X15终验已完成、最终代码摘要一致，且模型、反馈记账、时间与资源凭证均满足要求，可保留事件并进入冻结终评。策略版本为 `developer-oom-completed-native-v1`。

非开发容器OOM、cgroup整组OOM、不完整终验、非预算截止类异常或凭证不一致仍拒绝恢复；原生12小时截止产生的 `AgentTimeoutError` 按原规则允许。原 `passed: false` 和OOM计数保留在原审计及补充审计中。两个旧实例须经独立文件摘要绑定的人工审阅；五组新尝试采用同一修订口径。这是审计纠偏，不会增加可用内存，也不保证后续开发脚本不再触及32 GiB上限。

## 对 n=0 暂时领先的解释

现有结果不足以证明反馈有害。n=0仍有ABC公开评分；33次受保护反馈中32次组合分为0，主要提供可行性信息；900秒反馈与5400秒终评衡量不同运行点。各有反馈的最终版本都不同于历史受测版本，最后一次反馈后仍开发约3.8–8.4小时，存在后续修改退化与质量/资源成本取舍。n=0与n=1当前均分仅差约0.49%，完整结果每组仅1–2次，不能据此作反馈预算的因果比较。
