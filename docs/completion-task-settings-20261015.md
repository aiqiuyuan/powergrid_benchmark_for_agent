日期：2026-10-15。

## 2. 对五任务实施的直接影响

| task | 设置明确后最先核对／补什么 |
|---|---|
| GOC | 原生完整Code1→Code2、同基态、全故障、两阶段资源和官方checker；强方法未复现列覆盖限制 |
| UC | 复用原生包；评分端执行冻结solver生成新排程，再用独立validator；派生SCUC另列扩展 |
| RTE | 复用solver与checker；先选校准小测／C+X历史／独立泛化用途，再定面板和是否需要15/90分钟产物 |

已有UC／HEFTCom包附带源码，但当前评分主要读取静态排程／bids；“能够接入框架”与“在新输入上评测算法”需要分别核对。RTE既有真实模型canary保留其校准接入范围，不替代完整历史重评或泛化结果。

## 3. 发现并明确记录的问题

1. **selection并列规则存在既有分歧。** 评测协议建议较早受理，配置目录／独立参考实现采用较早完成。正式比较前需选择唯一规则并同步实际入口；本轮没有改代码或配置代作决定。
2. **原生共用评分入口不自动完成四角色隔离。** 反馈和最终评测使用同一个test.sh，需要核对实际可信阶段／成员绑定和公开selection；做不到时仅标校准或协议变体。
3. **模板存在反馈泄漏写法。** 评分样例把隐藏输入／expected拼进反馈，能源task不能照抄；本轮记录检查项，没有修改原模板。
4. **原生reward不等于能源原始指标。** 模板将reward限制在0–1，必须另保留raw metric，事前决定映射／截断／方向；合法负分不能被当作非法能源指标。
5. **公开tests目录仍然公开。** 真正隐藏的面板留可信运行端，GitHub保存来源／准备方法、split标识和必要摘要；目录隔离本身不构成数据保密证明。
