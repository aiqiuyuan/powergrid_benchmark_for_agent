## 2. 问题、输入输出与数据可见性

为每项电网维护干预选择合法开始时段，满足完成时间、资源上下界及季节互斥约束，最小化官方情景风险。输入包含完整 `Interventions`、`Resources`、`Exclusions`、`Seasons`、时间域、风险情景、Alpha 和 Quantile；不将原风险目标简化为均值或 CVaR。

令同一时段、同一情景下正在执行干预的风险之和为 R(t,s)，m(t) 为情景均值，z(t) 为官方分位值：

```text
F = Alpha × mean_t(m(t))
    + (1−Alpha) × mean_t(max(0, z(t)−m(t)))
```

F 越低越好，权威值由固定官方 checker 计算，不采信候选自报 objective。[官方题面、实例及 checker](https://github.com/rte-france/challenge-roadef-2020)

| 对象 | 开发／评测规则 |
| --- | --- |
| ABC45 | 开放全部原始输入及官方 checker，允许自由本地评分；计算及等待均计入开发 T |
| X15 | 输入、参考解、旧运行产物及排行榜答案不进入开发沙箱；正 n 仅能调用计数反馈接口 |
| 提交物 | 单个 `solver.py`，上限 1 MiB；各实例使用相同源码字节 |
| 输出 | 每项干预恰好一次，给出合法 1-based 整数开始时段；排程文件上限 4 MiB |
| 候选依赖 | Python 3.12、标准库、NumPy 2.2.6、SciPy 1.15.3；不临时安装依赖，无商业 solver |
| 随机性 | 两档执行 seed 均为 2020；三次重复是独立开发，不是三个执行 seed |

候选接口：

```text
python solver.py --instance INPUT --output OUTPUT --time-limit SECONDS --seed 2020
```

运行器一次读取候选源码，向 15 个独立 worker 传递同样字节，使用统一命名输入及新进程；不能逐例拼接 15 份程序。同一算法可按可见的规模、时域或资源特征选择策略。源码相同本身不证明不存在实例指纹，数据与旧答案隔离仍需单独核验。

ABC 原始输入共约 16.14 GB，X15 约 7.17 GB，总量约 23.31 GB；例如 B15 接近 4 GB，开发端应按需或流式读取。正式大数据及运行镜像按外部资产锁校验，微型验收输入不能代替完整工业实例。

X15 历史上已公开，当前工作区保护不会撤销模型先验接触；正 n 还允许适应同一面板。因此它是**受保护的自适应评测面板**，不声称从未参与开发的独立隐藏测试。

## 4. n 次反馈与开发分数

一次正式受理冻结一份源码，在 X15 每例运行 900 秒，完整面板结束后统一反馈，计 1 次 n；分别保存受理、完成、投递及 ACK。它不是一次模型请求或一个实例计分。n=0 没有开发期 judge／评分桥，但仍可在 ABC45 自测。

| 返回／保留 | 内容 |
| --- | --- |
| 逐例诊断 | 稳定实例 ID，AC／WA／RE／TLE，有效 F 及风险分项，约束分类，退出码，墙钟与 RSS |
| 面板汇总 | 覆盖数／比例、状态及约束统计、覆盖优先 reward、候选源码摘要 |
| 无效目标 | F 为 null，不填 0，不伪装为有效解 |
| 不返回 | X 原始输入、排程、原始日志或风险向量 |

固定开发反馈为：

```text
有效例 q_i = 0.5 − atan(F_i / scale_i) / π；无效例 q_i = 0
k = 有效实例数；Q = Σ q_i / 15
reward900 = (k + Q) / 16
```

scale 由原输入计算并冻结。该 reward 先比较覆盖数，再比较固定 15 例分母下的质量，越高越好；它不是原赛积分。基础设施缺输入、checker 故障或报告身份不符必须保留为错误，不将其伪装成算法零分或无记录追加免费反馈。

## 5. 截止终评与历史积分

框架停止开发，冻结**截止时当前 `solver.py`**；不自动回退到过程最高分版本。可信终评对同一 SHA256 产物分别运行 900 秒和 5400 秒，每档、每例独立启动；不是长轨迹上的短时快照。两个终评不占过程 n，不回流开发，5400 秒不用于选终态。

保留逐例 F900／F5400、状态与覆盖率，再按原赛工作簿口径计算：

```text
V_i = 0.8 × F900_i + (1−0.8) × F5400_i
b_i = 固定历史 13 队中，V_ki 严格小于 V_i 的队数
p_i = max(0, 10−b_i)
P = Σ_i p_i                         i = X01…X15；上限150
Z = 100 × (P−6) / (149−6)          不裁剪
```

每份程序单独对照原 13 队，不将 15 次开发互相加入为对手；同值不算严格优于，使用完整精度及工作簿浮点表达。固定端点不随新候选重新选择，也不按本批结果拟合。

失败时间档的原始 F 保持 null；仅积分计算代入 `1e99`，并按最终工作簿 `IF(V<>1e99,MAX(10−b,0),0)` 处理。双档失败为零分，单档失败仍可能获少量积分。规则文本的朴素贪心替代／不可行零分与最终工作簿有差异，本任务明确复现已公布工作簿，不虚构缺失贪心值。报告缺失或未完成执行属于基础设施错误，不能当作算法失败填进积分。

Z 表示相对固定历史积分区间的位置，不是风险目标质量完成百分比，也不是实际获得的原赛名次。它是当前交付主展示，原始 F、覆盖率、reward900 和后验采用时间同时保留。[固定历史参照及来源](sources.md)

## 6. 开发、评测与外层资源

| 层级 | 固定配置与计时含义 |
| --- | --- |
| 开发沙箱 | 2 CPU／32 GiB，存储声明 32 GiB，无 GPU，12 小时墙钟 |
| 单实例算法 | 固定一个可用 CPU；`RLIMIT_AS=17179869184` 字节，即 16 GiB **虚拟地址空间**，不是独立 RSS／物理内存配额 |
| 线程 | BLAS／OpenMP 默认单线程；候选自行开的线程共享该实例唯一 CPU |
| 面板评分器 | 15 CPU／256 GiB 共享内存，X15 15 路并行，存储声明 32 GiB |
| 外层作业 | 21 CPU／296 GiB，覆盖开发、评分及系统余量；Linux amd64、Harbor 0.20.0、专用 privileged DinD |
| 共享内存与磁盘 | `/dev/shm` 8 GiB；临时存储 request／limit 128／256 GiB；node-local Docker emptyDir 上限 224 GiB，启动前实际空闲至少 128 GiB |
| 单例时限 | 900／5400 秒外部墙钟，包含启动、导入、解析、建模、求解和写出 |

15 路是实例级并行，不增加每例 CPU 配额，不代表独占 15 颗物理核；共享磁盘、内存带宽及节点负载会影响速度。外部模型推理和受保护评分器也不计入本地开发 2 CPU。

原赛评测声明 Linux、2 CPU、16 GB RAM，允许 CPLEX／Gurobi／LocalSolver，使用共同随机 seed、专用机器顺序测试。当前为每例单核、16 GiB 地址空间、现代容器及 15 路并行，无原机吞吐校准；不能由 CPU 数推导时间倍数，也不能认为地址空间限额等于原赛 RAM。原赛未给出统一团队研发硬件／实际净工时上限，当前 12 小时不能解释为同开发投入比较。[官方规则](https://github.com/rte-france/challenge-roadef-2020/blob/master/Challenge_Rules.pdf)、[决赛提交要求](https://roadef.org/challenge/2020/en/finalSubmission.php)

## 7. 时间估算与校准依据

| 环节 | 固定预算／规划估算 |
| --- | --- |
| 开发 | 43200 秒／12 小时；ABC 自测、模型交互和反馈等待均占时钟 |
| 一次 X15 过程反馈 | 单例算法最多 900 秒／15 分钟；15 路并行，因此不能把 15×900 秒当面板墙钟 |
| 过程基础设施 | 每例数据准备／worker 预留 120 秒、checker 180 秒；runner 1500 秒，verifier 1800 秒 |
| 900 秒独立终评 | 另一个完整面板，与过程同算法预算；不回流 |
| 5400 秒独立终评 | 算法阶段最多 90 分钟／面板，runner 上限 6300 秒／105 分钟；排队、镜像及额外编排另计 |
| 双档候选计算量 | 每份截止程序最多 `15×(900+5400)=94500` CPU 秒，即 26.25 CPU 小时；不是日历耗时承诺 |

已有完整 X15 资源门禁墙钟 **924.565 秒**，约 15.41 分钟，包含超时／失败实例；它是原 v5 数值资源校准，不是 v2 新算法的吞吐承诺。900 秒原生终评结束后才执行 5400 秒补充档，**两档串行复用同一评分资源额度**，不要求额外并发 30 CPU；每档内部仍为 15 例并行。

十次完整 900 秒过程反馈的纯候选工作最多 37.5 CPU 小时；15 路串行轮次的算法墙钟约 2.5 小时，基础设施、排队及自适应开发另计，不能保证任意运行用尽 n。若全部分组用满，最多 57 次过程面板另加 15 份双档终评；候选阶段合计上限约 607.5 CPU 小时，不包含开发、checker、数据加载和系统工作。此处均为合同预算推算，不是新跑出的速度测量。

资源校准曾在每例 8 GiB 地址空间出现 3 个 MemoryError，因此在正式 n 比较前统一改为每例 16 GiB、评分器 256 GiB、外层 296 GiB，并通过完整 X15 门禁。该门禁采样最大 `memory.current` 为 95,561,768,960 字节，`memory.peak` 不可用；采样值为下界，不当真实峰值。资源门禁证明该配置可执行完整面板，不证明 starter 全例可行，也不约束所有未来算法内存需求。[历史配置及校准记录](../protocol/rte-abc-x15-configuration.md)
