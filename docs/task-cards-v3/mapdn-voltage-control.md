# MAPDN：原生多智能体 RL 电压控制

> 本卡冻结口径：2026-10-21，当前正式版本为 **CPU RL v9**。这里只定义任务、比较基线、反馈、测评、资源与耗时；不填写本轮正式演化结果。另行准备的 GPU 版本不属于本卡。

本轮给开发者可实际交互的原生训练环境，使其能够训练多智能体策略，而不只是在单个固定日上修改规则。各 n 组使用相同的 No Control 初始提交目录，不赠送作者训练权重；可自行训练或改用其他控制方法。训练允许集中式状态与 critic；执行保持去中心化：六个 PV actor 分别读取自己的局部信息并输出无功控制动作。研究对象是这套训练与执行合同下、跨独立日期的策略质量。

## 2. 问题定义、输入与输出

MAPDN33 是含六个可控 PV 单元的配电网电压控制问题。每 3 分钟的负荷与 PV 有功变化后，控制器调节各 PV 的无功功率，在电压安全与线路有功损耗之间取得平衡。

| 阶段 | 允许输入与操作 | 输出 |
|---|---|---|
| 训练 | 原作者 `reset`、`step`、`get_obs`、`get_state`、`get_avail_actions`；可访问训练视图的集中式状态 | 训练代码、六个局部 actor 及其权重；也允许传统局部控制器 |
| 执行 | 各 actor 自己的原生局部观测、允许元数据及本 episode 私有历史 | 每个 actor 一个 `[-0.8, 0.8]` 动作，由可信环境映射为该 PV 无功 |
| 提交 | 完整 `controller.py`、权重、预处理及所需本地文件 | `Controller(metadata, artifact_dir).act({native_obs: local_vector}) -> [action]` |

执行时不向 actor 提供集中式 critic 状态、其他 actor 私有历史、验证/测试原始数据或评分器内部状态。每个 episode 从同一冻结初始产物启动新的隔离 actor 进程，episode 间不继承适应状态。训练中的额外观测权限不能延伸到最终执行。

最终目录最多 **256 MiB、2048 个文件/目录项、12 层目录**；链接与特殊文件拒绝。普通缓存文件属于目录内容并参与哈希与大小核验。冻结包括代码与权重，终评使用截止时认证的当前目录；不回溯选择历史反馈最好的 checkpoint。

## 3. 数据、训练与测试划分

原始时间范围为 2012—2014 年。每个自然月按完整日连续划分：前 `floor(0.70 × 完整日数)` 日训练，随后 `floor(0.15 × 完整日数)` 日验证，其余完整日测试。部分日排除；episode、原生历史窗口与边界余量均不得跨分区日期块。

| 数据角色 | 当前合同 |
|---|---|
| 公开训练 | 仅公开 train 视图；环境交互和训练诊断在开发时间内不限次数，不消耗 n |
| 受保护反馈 | validation 分区固定 36 个 episode，每月一个合法窗口；完整执行 479 次转移 |
| 最终测试 | test 分区固定、同顺序的另 36 个 episode；日期和 reset seed 与 validation 分离 |
| 训练时域 | `episode_limit=240`，实际 239 次训练转移；保留训练 step 噪声 |
| 反馈/测试时域 | `episode_limit=480`，实际 479 次转移；保留原生 reset 扰动与初始无功抽样，step 不额外加噪 |
| 共用统计量 | PV 最大值、噪声尺度与 `Smax=1.2 × 训练 PVmax` 仅由 train 拟合，三分区共用 |

固定面板 reset seed 为 validation=`20000+j`、test=`30000+j`，`j=0…35` 对应固定月序；它们与三个独立开发重复、baseline 的五个训练 seed 分别记录，不互相相乘。

这是**按月分层的独立日期留出**：训练集合包含较后月份，不能称为整个时间轴上的严格未来预测。它也不是原论文历史随机测试协议的逐项复现。输入网络、静态参数、数据快照和面板按清单锁定；同一候选的全 36 episode 必须完成，不以截短 episode 或成功子集代替。

## 4. 可比 baseline 与比较边界

比较集合在查看新测试分数前固定为 **No Control、COMA-L1、MADDPG-L1、MATD3-L1**。后三者来自原作者开源实现，覆盖 Table 3 预先选定的三种非支配 L1 方法。

| 比较项目 | 固定规则 |
|---|---|
| 学习方法重复 | 每方法训练 seed 0/1/2/3/4，全部纳入 |
| 训练预算 | 每 seed 400 episode，即 95,600 次训练转移 |
| checkpoint | 最后完成的 checkpoint；不按测试分数挑 checkpoint 或 seed |
| 推理 | 导出六个局部 actor，使用候选相同的观测、动作、独立进程及 CPU judge |
| 面板与统计 | 每 seed 先汇总完整 36 episode，再对固定五 seed 等权求方法均值 |
| v9 基线来源 | 接纳已完成的 v5 训练及完整测试，保留原 UID/权重/来源；没有重新训练或改标为 v9 生产 |

这支持**同数据划分、同信息、同动作、同测试面板、同指标与评分资源的策略质量比较**。400 回合固定训练与 12 小时任意演化不具有相同训练计算量；原论文 Table 3 历史数值只作背景，不作为当前测试表现的替身。传统全信息 OPF 及具有额外内部潮流机会的历史 droop 不在这组同权限 RL 比较中。

## 5. n、过程反馈与终评

n 限制不同完整候选在**受保护 validation 36 episode** 上取得评分的次数，与训练次数和 token 使用量独立。相同产物字节及评分上下文返回原回执，不多扣一次；候选自身失败会消耗预算。未完成调用须核对原身份，不能靠换 key 获得免费重跑。反馈仅交付 `status / valid / score`；训练 reward 和训练诊断不是该反馈。

等待反馈占用原开发时钟。截止后结果不得影响冻结产物。n=0 没有受保护过程反馈；它仍有完整训练环境。截止先停止全部写入者，在 15 秒预留内捕获与认证当前产物；随后在**独立 test 36 episode** 上重新执行，不消耗过程 n，也不回传给开发者。

有效性要求所有 episode 均完成 479 次转移，没有原生 destroy 或 actor 错误。CR、PL 先按每 episode 的完整轨迹计算，再对 36 episode 等权平均。候选失败和基础设施未完成分别记录；不能删去坏 episode 后计算平均。

## 6. 指标与两套标尺

主要原始指标为 **CR ↑**：全部 33 母线同时位于 `[0.95,1.05] p.u.` 的时间步比例；**PL ↓**：平均线路有功损耗，单位 MW。原生 return 另存，不替代 CR/PL。

开发反馈保留事先冻结的 Table 3 缩放信号，不裁剪：

```text
feedback = 0.5 × 100 × (CR − 0.706) / 0.294
         + 0.5 × 100 × (0.069 − PL) / 0.013
```

最终比较以新测试面板上的 No Control 为 0 分，各指标最佳**方法均值**为 100 分，先对五 seed 聚合再选方法锚点，不选最好单 seed。

```text
CR_norm = 100 × (CR − 0.7258176757132916)
                / (0.9509394572025052 − 0.7258176757132916)
```

其中 CR 高锚点为 COMA-L1 方法均值。PL 的预定公式为 `100 × (NoControl_PL − PL) / (NoControl_PL − best_method_mean_PL)`，但仅在最佳方法均值严格优于 No Control 时定义。当前最低方法均值 PL 为 MATD3-L1 的 `0.06779034008380874 MW`，仍高于 No Control 的 `0.06742760627554109 MW`，因此 **PL_norm 与 CR/PL 等权综合分均为 N/A**；继续报告原始 CR、PL 与 CR_norm。不能反转锚点、挑有利 seed 或拿过程反馈填补 N/A。上述数字是评分定义所需基线锚点，不是本轮正式演化结果。公开[基线定标摘要](evidence/mapdn-baseline-anchors.json)保留完整方法均值与 N/A 规则。

## 7. 资源合同

| 层级 | CPU / 内存 / GPU | 用途 |
|---|---|---|
| 开发与训练容器 | 3 CPU / 8 GiB / 无 GPU；PyTorch CPU 单线程配置 | 代码开发、训练、训练诊断共用 |
| 验证与最终 judge | 2 CPU / 8 GiB / 无 GPU | 同镜像执行完整面板；不是每 actor 各分配此额度 |
| actor 进程 | 每进程地址空间 4 GiB、CPU 时间 120 秒；初始化 45 秒、一次动作 RPC 2 秒 | 另受共享 judge 总内存/CPU 与每 episode 600 秒上限约束 |
| 正式外层 Job | dev，request=limit 8 CPU / 32 GiB / 无 GPU | 开发、judge、可信控制及专用 DinD 的整体封套 |
| 产物与存储 | 产物 256 MiB；DinD emptyDir 128 GiB；ephemeral request/limit 128/256 GiB | 存储声明不是整段开发原始日志的硬磁盘配额 |

运行依赖为冻结的 Python 3.12、PyTorch 2.9.0、Pandapower 3.3.0 体系；原作者源码来源锁定于 `eb257c975ff0c94ee3c00991866d4705f29fea18`。开发容器无网络和提供方凭据，评分器与目标数据留在可信侧。三个固定反亲和槽限制每节点最多三个本 campaign 正式 Pod，排除 dev 节点 67/68/73/77，初始化串行；这不保证无共享磁盘或 CPU 争用。

## 8. 耗时与完成时间估算

| 项目 | 实测 / 合同及其解释 |
|---|---|
| 开发 | 上限 12 小时，含 15 秒冻结；提前正常结束可以短于上限 |
| 单次完整终评校准 | v9 fresh native n0/n1/model n0 分别 **720.27 / 647.28 / 674.49 秒**，约 10.8—12.0 分钟；均完整 36×479 |
| 单次反馈工作量 | 同规模 36×479 validation；可用上述成本作规划参考，但它不是验证分区或任意候选的耗时保证 |
| 一次面板硬上限 | **21,660 秒 = 6 小时 1 分钟**；这是上限，不是期望耗时 |
| 冻结链校准 | 最大允许产物的停止、流式捕获及本地认证实测 2.2458 秒，位于 15 秒预留内 |
| 最大反馈传输校准 | 合成大产物完整传输链 240.7551 秒；不等于真实面板评分耗时 |
| 外层 watchdog | 172,800 秒 / 48 小时，覆盖启动、开发、末评与清理；不扩大 12 小时开发额度 |

若 n=10 全部顺序调用且每次恰好接近上述终评校准，则单纯评分约 1.8—2.0 小时，另加上传、启动与竞争成本；这不是已测十次反馈总时长。n 表示最多可用反馈，不保证截止前用满。没有排队时，一次完整上限开发加一次校准规模末评约 **12 小时 12 分钟 + 启动/传输/清理**；实际完成时间还需加资源排队，15 个独立重复不保证同时启动。任何候选都可能比参考控制器慢，规划须保留硬上限与基础设施失败的区别。
