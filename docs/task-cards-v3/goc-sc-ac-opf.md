# GOC：公开 20 场景的通用 SC-AC-OPF 算法

> 整理日期：2026-10-21（北京时间）。本卡记录当前正式协议、比较基线和资源预算，不汇总正式演化结果。

## 2. 问题定义、接口与可见数据

求解完整两阶段安全约束交流最优潮流。基态决策包含机组有功／无功、母线电压幅值／相角、可控并联电纳；每个原始故障还需产生相应交流状态及机组响应。保留机组跳闸、支路退出、区域参与、出力饱和和无功响应等原始规则。

单场景目标为未修改的官方目标：

$$J_i=C_{\mathrm{base},i}+P_{\mathrm{official},i}(x_0,x_1,\ldots,x_{K_i}).$$

成本及功率失配、支路越限等软惩罚按官方公式计算。**硬可行与软罚分分开**：软罚分非零不自动表示硬不可行，输出可解析也不自动表示硬可行。

| 阶段 | 统一源码入口 | 必须产生的结果 |
|---|---|---|
| Code1 | `python /submission/code1.py` | 当前场景完整基态 `solution1.txt`，可附本场景中间状态 |
| Code2 | 新容器执行 `python /submission/code2.py` | 读取本次 Code1 的只读 `/stage1/`，输出覆盖全部原始故障的 `solution2.txt` |
| 官方评分 | 独立受保护 evaluator | 格式／覆盖／硬约束检查，原始 `J`、cost、penalty 和逐状态诊断 |

开发端可读 `/app/panel.json`、全部 `/app/cases/scenario_*/` 原始 RAW／ROP／INL／CON 和 `problem.json`、官方公开数学与格式文档，以及允许的序列化 API／Julia 数值工具。数值执行只呈现当前场景为 `/app/problem.json` 和 `/app/native/`，通过 `GOC_APP`、`GOC_OUTPUT`、`GOC_STAGE1` 等环境变量访问。

同一冻结源码在每场景的全新隔离环境中执行；场景之间不共享可写缓存，Code2 不得修改 Code1 基态。源码闭包最多 **60 MiB／10,000 个普通文件，无链接**。不得提交缓存答案、预存运行点或逐场景解表；允许按当前负荷、设备及网络特征选择算法分支和共享参数。

所有组均可依据公开规格编写代理、全量本地估分器和物理诊断程序，这些自主计算不计入 `n`。官方 evaluator 实现、评分凭据、历史解、其他运行产物和私有编排实现不对开发者开放。数值容器无网络、模型 API 或开发目录访问。

## 3. 比较基线与可比边界

| 参考 | 当前用途 | 可比范围 |
|---|---|---|
| 共同通用 starter | 全部 `n` 的相同初始源码；Code1 裁剪原始控制到盒边界，Code2 使用通用 PMSC strict fixed-point 故障求解路径 | 同一完整 20 场景、资源与两阶段时限；不是用旧演化程序初始化 |
| 历史 `ARPA-E Benchmark` | 同网络完整 20 场景的官方历史参考，作为历史尺度的 0 点 | 有原始官方成绩；未在本轮硬件上重跑 |
| 历史完整单队 `gravityx` | 该网络 20 场景历史最佳完整单队，作为历史尺度的 100 点 | 采用一支队伍完整面板，不拼接逐场景冠军；不是原赛全网络总榜 |

当前通用 starter 已通过 source-matched 完整面板验收；它提供可执行起点，不代表强基态经济优化，也不保证低软惩罚。PMSC 是可用数值工具家族；旧版其他网络上的 PMSC 实跑不能自动变成本面板的同条件强基线。

历史辅助对照沿用此前固定的公式：先算完整 20 场景的 `G=exp(mean(log J_i))`，再算

$$S=100\,\frac{G_{\mathrm{Benchmark}}-G}{G_{\mathrm{Benchmark}}-G_{\mathrm{gravityx}}}.$$

固定历史锚点分别为 `584181.286636799341` 与 `350038.111587336170`。保留负分和超过 100 的值；不平均逐场景归一分，不用有效子集均值。该辅助历史尺度**不替代下节当前开发任务的算术均值与覆盖优先排序**。历史硬件、软件和执行条件不同，不能据此声称等算力胜出或恢复原赛官方排名。

## 4. 过程反馈、终评与权威指标

一次受理将源码与评估合同冻结，对全部 20 场景执行，**完整批次消耗 1 次 `n`**。已受理后的算法报错、超时、已证实 OOM 或缺输出仍占该次机会；其他场景继续执行。相同源码／合同重提返回原批次，读取或分页报告不扣次数。跨独立开发重复不共享候选结果缓存。

`n=0` 没有官方 submit／result／status 服务、工具或评分 socket，也不预装官方 starter 成绩。它仍可使用公开输入和自写估分器。完整批次发布前只提供进度，不泄露部分场景成绩；候选失败构成明确失败行，基础设施缺失则标记 `infrastructure_incomplete`，不生成成功子集分数。

记 `F` 为有效且硬可行场景数，`V` 为有效场景数。权威比较器 `coverage-hard-meanJ-v1` 按以下次序：

1. 最大化 `F`，再最大化 `V`。
2. `V=20` 且 `F<20`：最小化 `Hmax`，再最小化 `Hmean`。每场景超差为 `e_i=max(0, max_nonobjective_violation_i−10⁻⁴)`，两者为完整面板最大值与均值。
3. `F=20`：最小化完整面板算术均值 `M=ΣJ_i/20`。官方 `J_i` 内部已有故障权重，不按 `K_i` 二次归一。

`V<20` 且 `F`、`V` 均相同时并列，不拿可评分子集的成本破同分。缺失值为 `null`；框架 scalar reward 仅供显示，不决定选优。硬可行覆盖优先意味着 20 个硬可行但成本较高的方案优于仅 19 个硬可行的方案。

反馈包含全部 20 行处置、J／cost／penalty、硬超差、故障覆盖、阶段时间、错误原因，以及相对上次完整反馈的变化。完整报告保留官方 37 列逐状态诊断、每类约束最大残差和对应设备／故障定位。首屏 **16 KiB**，文件分页 **256 KiB**，报告总上限 **64 MiB**，客户端校验文件与分页哈希。

最大残差及 argmax 不代表所有设备残差、违规设备总数或逐类罚分贡献；官方逐行累计 `obj` 也不能当作单故障 J。反馈只公开已计次结果的规范化诊断，不开放评分实现。

开发停止后，认证并冻结唯一最终源码，另做一次 **fresh 全 20 场景终评**，不消耗过程 `n`，不使用过程缓存替代重算，不向开发阶段回流。基础设施恢复限于同一身份／源码／原时钟，最多 2 次附加尝试，保留全部失败。报告保留每档全部 3 次开发重复；若选代表算法，须选一份完整面板源码，不能逐场景拼接。

## 5. 开发、求解与评分资源

| 层次 | CPU | 内存 | 资源及计时口径 |
|---|---:|---:|---|
| 开发容器（inner） | 8 | 32 GiB | 无 GPU，固定模型通过受控网关访问 |
| 开发 Job（dev outer） | request 2／limit 10 | 48 GiB | request 是调度份额，不能视为持续 10 核吞吐保证 |
| Code1／Code2（inner） | 24 | 56 GiB | 每阶段独立容器，全部后代受宿主时限约束 |
| 官方 grader（inner） | 2 | 16 GiB | 每场景独立评分上限 3,000 s |
| 数值 Job（center outer） | 26 | 96 GiB | campaign 共享最多 20 个数值 Job，轮转准入 |

单批独占全部 20 槽时，外层总请求可达 **520 CPU／1,920 GiB**；多个开发者共享这个上限，不是每个开发者各拥有 20 槽。开发 Job 排除已确认不适用的 4 个节点，采用三槽 required anti-affinity 和串行初始化，每节点最多 3 个本 campaign 开发 Pod。

外层 ephemeral-storage request／limit 为 **128／256 GiB**，不等同于实际空闲磁盘保证。候选运行、官方评分和开发资源分开记账；采样内存峰值只是真实峰值的下界。

## 6. 时间预算与规模估算

| 时钟 | 配置／解释 |
|---|---|
| 开发 | 最多 172,800 s／48 h，从实际安全开发开始计，含过程反馈排队、执行、等待及报告读取；可实质完成后提前结束 |
| Token | 无累计 cap、预留或 token 触发终止；记录实际 provider 用量 |
| 每场景 Code1 | 600 s，包含启动、编译与子进程 |
| 每场景 Code2 | `2K_i` s 合计，即 1,386–1,522 s；不是每个故障重新给一份总时限 |
| 官方评分 | 每场景最多 3,000 s，独立于两阶段候选计算 |
| 编排保护 | 数值执行 watchdog 6,400 s，排队保护 172,800 s；不扩大候选时限。开发 outer watchdog 518,400 s 也不是开发预算 |
| 截止后终评 | 开发时钟之外重新计算全 20 场景，排队、执行、评分与归档另计 |

按配置上限，一完整面板两阶段合计 `20×600+2×14554=41,108 s`，即 **11.42 个累计求解小时**；再加所有 grader 上限为 **28.09 个累计场景任务小时**。这两项是串行预算之和，不是实测墙钟。

若单批立即取得全部 20 槽且无故障，最长场景的求解加评分预算为 `600+1522+3000=5122 s`，约 **85.4 min**，另加启动、传输和归档。共享排队、基础设施恢复和报告交付会延长等待，因此不能把该理想并行估算当成完成承诺。

实际完整报告交付已测：42 文件、28,872,564 bytes、142 页，客户端领取并验证全部哈希耗时 **292.877 s**。这是报告访问校准，不是完整数值批次运行时间；当前本卡不把旧单场景耗时推作通用算法速度。

| 调用规模 | 过程场景执行 | 终评场景执行 | 合计 |
|---|---:|---:|---:|
| 一次开发，预算 n | `20n` | 20 | `20(n+1)` |
| 五档 n 各 3 次，均用满 | 1,140 | 300 | 1,440 |

最大设计量等于 57 个过程面板加 15 个终评面板；不含校准、验收和基础设施恢复。新的 `n=1` 含 20 场景信息，与旧单场景 `n=1` 的计算量和信息量不同，需同时报告面板数、场景数、实际资源时间和模型用量。
