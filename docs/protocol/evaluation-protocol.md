具体问题定义与校准计划见五张任务卡：[GOC SC-AC-OPF](../task-cards/goc-sc-ac-opf.md)、[UC/SCUC](../task-cards/unit-commitment.md)、[RTE maintenance](../task-cards/rte-maintenance.md)、[L2RPN](../task-cards/l2rpn-grid-control.md)、[HEFTCom](../task-cards/heftcom-forecast-trade.md)。

文中的“必须”是未来正式版本的验收要求。当前仓库提供文档与声明，不提供已经实现这些要求的执行器、密封数据或正式排行榜。数据清单、镜像摘要、预算和基线尚未实测冻结的配置不能用作正式实验发布。

## 1. 从预实验中明确改变的规则

| 预实验暴露的情况 | v0.1-design 的决定 | 对历史结果的处理 |
|---|---|---|
| 多个任务在运行中和结束时使用同一面板 | 第一阶段明确采用同case，冻结后独立执行复核；第二阶段才要求泛化留出 | 旧结果可描述其原条件下的自适应优化；不能重新声称未见泛化 |
| UC/SCUC 验证静态调度，不执行提交的求解器 | 最终复核实际执行冻结求解器，并独立检查固定case输出 | 静态调度结果说明可行性与当前实例成本，不说明求解器泛化 |
| HEFTCom 当前 grader 对预先生成的 `bids.csv` 评分，不重新执行预测与交易代码 | 在固定case因果时段执行冻结特征、预测交易流水线，再独立计算收益 | 静态 bids 分数保留为历史回测校准，不证明流水线在新时段可重放 |
| `n` 已用与模型收到反馈不一致，个别数值任务已结束而账本仍显示运行 | 分开记录受理、执行、完成、投递和重试 | 不把“用了 n 次”当作“得到了 n 次有效反馈” |
| 部分实验受累计 token 配额提前终止 | 新版本只采用统一开发墙钟时限；token 用量只用于统计 | 保留旧配置，不与新版本直接合并为同一预算组 |
| judge 的计时起点早于完整开发上下文准备 | 准备完成后，协调器产生一次共同的 `development_start_at` | 历史耗时按原起点报告，不事后补发开发时间 |
| 旧运行协议内部把 evaluation budget 的数值 0 用作“不限次数” | 本协议 `n=0` 明确表示没有受保护反馈；不限次数必须使用单独模式 | 执行器适配时必须消除 0 的歧义，不能直接沿用旧内部参数 |
| 完整checker或本地评分使n失去受控变量含义 | 第一阶段禁止开发agent获得完整checker、搜索原赛测评源码或本地取得目标case完整分数 | 旧公开自测政策属于旧协议；不据此追溯认定违规，也不沿用到新批次 |

## 2. 第一阶段固定case与信息权限

### 2.1 同case研究范围

每task先固定一个完整case，优先选择规模／约束复杂、成熟基线仍有可改进空间且能在预算内执行的高难case；不能在看到agent比较结果后挑更有利的case。RTE已初选工业case X04，依据原赛13队15／90分钟有效数6／7；完整运行成本、输入权限与算法限额仍须校准冻结，见[X04配置](rte-x04-configuration.md)。开发、所有计数反馈和截止复核使用同一case与相同评分合同。其他case用于第二阶段泛化，不是第一阶段启动前置。

同case原始分数可以与原榜该case成绩对照；执行条件不同则标历史参照，不能由单case成绩推导原赛总榜名次。已暴露case可用于此主线，但必须准确披露自适应使用范围。

### 2.2 评分访问边界

完整目标评分只能经框架受n控制的反馈接口进入开发过程。不得把完整checker、等价完整评分工具或可读分数日志放进开发端；禁止搜索原赛测评源码。语法、格式和小型示例检查允许且计入T。不能把完整目标评分改称“public-selection”或“公开自测”从而免计n。

这条政策约束向开发agent提供评分反馈，不禁止solver在可信执行内计算内部目标、风险或增量目标。目标case数据是否在开发端可见仍须结合防绕过能力确定，不能从“同case”推导全部输入和checker都可见。最新分支已查到域名黑名单／搜索限制能力；实际启用与直连、本地副本、自己重写完整评分等旁路仍须验收，单个域名代理不能证明全部禁止项已强制实现。

### 2.3 case清单与calibration

每task用现有说明记录case ID／摘要、原题完整性、难度依据、开发可见文件、完整评分端持有文件、算法预算／资源／seed及反馈字段。第一阶段不要求四份互斥split；仍保留来源、暴露和版本记录。成本／难度测量标为calibration，不能把测得的最好算法成绩当未参与开发的独立验证。

<a id="2-四种数据角色与-calibration"></a>

### 2.4 第二阶段参考：四种数据角色与 calibration

以下保留旧泛化设计以便追溯，不适用于第一阶段，也不代表第二阶段已经批准免费checker／selection评分；下一阶段须重新确认评分权限。此小节中的“主线”仅指旧设计。

<a id="21-数据角色"></a>

#### 数据角色

| 角色 | 对开发智能体可见的内容 | 允许的用途 | 禁止的用途 |
|---|---|---|---|
| `public-development` | 实例、训练标签、参考代码、公开 checker | 编写、训练、调试、任意本地测试 | 混入密封测试标签 |
| `public-selection` | 实例及公开评分信息 | 在开发时限内选择候选；默认 selection 依据 | 作为最终泛化分数 |
| `protected-feedback` | 仅可通过受预算控制的评测接口获取预先声明的反馈 | 开发期自适应改进；受 `n` 和 `T` 约束 | 直接挂载输入、标签、缓存或评测私有状态到开发容器 |
| `final-test` | 开发期间不可见；冻结后由评测器提供必要的单实例输入 | 对冻结算法做一次最终评测 | 调整算法、选择 checkpoint、重新训练或挑选最有利的重复 |

`calibration` 是**发布前的数据用途标记**，不构成第五种正式实验反馈权限。旧预实验已经暴露的数据、已反复用于调参的面板和用于测运行成本的样本均标记为 calibration，不得重新命名为“从未使用的 final-test”。

公共数据可能已存在于模型预训练语料，不能保证模型从未见过。这里的“密封”表示实验期间的访问边界和预先封存的切分，不表示数据在互联网或预训练历史中不存在。论文必须同时披露公共来源、暴露风险与实际隔离措施。

主线 ML 参数拟合只使用 `public-development`；`public-selection` 的标签与评分用于模型/候选选择，不用于重新拟合权重。如果研究需要开发加 selection 数据的重新训练，必须使用另一个 `protocol_id`，预先声明权限和解释限制，并在 `T` 内完成。重新训练产生新的 artifact，须在截止前完成该产物自身的 selection 评测并重新冻结；旧权重的 selection 记录不能代替新权重证据。任何方案均不得用 `protected-feedback` 或 `final-test` 标签拟合。

<a id="22-切分清单"></a>

#### 切分清单

每个发布版本必须包含可审计的 split 清单，至少记录：

- `split_id`、`task_id`、`task_version`、`dataset_version`、`split_strategy`。
- 每个样本的稳定标识、来源、内容摘要、`group_id` 和数据角色。
- 分组规则、切分 seed（若随机）、时间边界、时间间隔及其依据。
- 各角色样本数、适用实例范围与校准用途；密封项的公开承诺摘要与评测端保存的完整清单。
- 标签、协变量、输入文件、衍生实例和缓存的可见性声明。

公开仓库可以只保存 final-test 清单的承诺摘要；完整密封清单由评测端保管。发布冻结后，不能为配合算法结果改变样本成员、权重或随机种子。若切分变化，生成新的 `split_id`，整批比较使用新协议。

<a id="23-先分组再切分"></a>

#### 先分组，再切分

不能简单把实例文件随机分成四份。先识别同源数据，再在合适的分组层级分配角色：

| 任务类型 | 分组原则与必须记录的边界 |
|---|---|
| GOC、UC/SCUC | 同一网络、原始调度日期、基础输入及其扰动实例建立来源关系；用于跨拓扑评测时，整个拓扑族只进入一个角色；同一基础实例的裁剪、扰动和重复不得跨角色 |
| RTE | 同一原始维护实例的变体、资源重标定或场景子集保持同组；必要时按规模/约束模式分层，而非把近乎相同的文件拆开 |
| L2RPN | 同一 chronics、连续时段、重复 seed 和相邻派生窗口保持同组；按时间块切分并隔离重叠窗口 |
| HEFTCom | 按时间顺序切分；特征、标签窗口与训练目标不得跨边界；时间间隔由预测期、最大滞后和标签可用时间共同确定 |

拓扑可以在**明确声明的同拓扑时间泛化**协议中共享，但同源样本和重叠窗口仍不得跨角色。该协议不能声称跨拓扑泛化。跨拓扑与同拓扑时间泛化需要不同 `split_id` 和独立结果表。L2RPN 的单环境主线首先报告时间泛化；多拓扑是后续扩展。

HEFTCom 当前使用的时间间隔可以作为校准起点，不能因为预实验采用过某个固定天数就认定不存在泄漏。任务发布前需审查所有特征的生成时间及预测时刻可用性。

## 3. 正式运行单位与比较条件

一个 run 由下列不可变配置共同定义：

`task release + case_id/内容摘要 + protocol_id + agent/algorithm version + model version + seed + resource profile + T + n + final-artifact policy + feedback schema`。

`run_id` 标识一个运行；`cohort_id` 标识预算与恢复政策相同的比较组。随机重复属于独立 run。UC 和 SCUC 的数据适配、GOC 的规模档位、L2RPN 的不同环境必须作为可辨认的子设置保存，不能把版本差异隐藏在任务名称中。

默认比较固定任务发布、模型及其单次输出上限、开发资源、开发时限、候选选择政策和失败处理，只改变被研究的变量。多智能体共享总开发资源与反馈配额；增加代理数不自动增加 `T`、`n`、CPU、GPU 或内存。

训练型算法与纯代码智能体可报告同一任务下的结果，但“公平预算”必须说明：固定墙钟与资源并不等于固定 token、训练步数或算法工作量。评测等待计入开发时限，这一成本属于协议的一部分。

## 4. 开发时限、评测时限与 token

### 4.1 唯一开发时钟

准备阶段包括：拉取已冻结镜像、安装已声明依赖、预编译共同基础环境、验证任务包，以及挂载开发可见上下文。准备阶段只能运行基准统一规定的工作，不能提前执行智能体、候选搜索或任务特定训练。

准备完成后，协调器记录 `development_start_at` 并同时开放开发权限。`development_deadline_at = development_start_at + T`。agent、judge、续跑器、训练进程和 watchdog 使用同一截止时间；服务重启不重置时钟。必须同时记录 UTC 时间戳和相对耗时。

`T` 包括模型请求、智能体思考与工具调用、候选编译、训练、允许的轻量本地检查、计数完整评测等待以及开发期间故障造成的等待。启动前的共同环境准备与冻结后的最终评测不计入 `T`，但单独记录成本。

到达截止时刻后停止开发侧计算与写入，冻结原生artifacts路径中的最终候选。等待中的评测可以完成并留档，但不得继续向开发智能体投递，不能唤醒智能体修改算法。每次投递都必须检查同一个截止时间；仅在提交时检查不够。

开发时限 `T`、单次反馈评测时限、最终构建时限、逐实例/逐 episode 最终时限、最终批次总时限均必须在 task release 中填实。没有完成校准的占位值只供设计讨论，不能自动发起正式批量运行。

### 4.2 token 政策

新正式协议**不设累计 token 上限，不做累计 token 预留，也不因累计 token 用量提前结束开发**。单次响应上限、上下文窗口与供应商限流仍需声明。记录 provider 实际输入、输出、缓存 token；不可得时标记 unknown，不能填零。

历史使用累计 token 上限的 HEFTCom、UC/SCUC 和 L2RPN 实验保持原配置，作为独立 calibration cohort。新时间预算实验使用新版本，不能补改历史配置以制造预算一致性。

## 5. 受保护反馈预算 `n`

`n` 是**最多受理多少个受保护评测作业**，不是演化代数、候选数量、内部 solver 迭代数或保证得到多少条反馈。`n=0` 仍可使用合法开发材料、轻量示例及非评分工具，但不能获得目标case完整评分；过程评分接口必须拒绝其提交。冻结后终评仅作报告，不回流开发。

正式评测默认串行处理同一 run 的 protected-feedback 作业；在已有作业未终止时，新的提交拒绝且不扣次数。需要并行反馈时，应定义另一个 `protocol_id`，统一改变所有比较组。

### 5.1 计数规则

| 情况 | 是否占用一份 `n` | 记录与处理 |
|---|---|---|
| 完整、符合提交契约的快照被受理 | 是 | 受理与扣次原子化落盘，生成稳定作业标识 |
| 受理后候选语法错误、崩溃、超时、不可行或得零分 | 是 | 结果属于候选失败；保留具体错误和评分 |
| 受理后评测基础设施故障 | 是，历史占位保留 | 同一快照可按预先声明政策重试原作业，不再次扣次 |
| 智能体没有取回结果、投递失败或开发截止后完成 | 是 | 单独记录未投递原因，不能退回配额 |
| 包损坏、必需文件缺失、规格不符，受理前拒绝 | 否 | 记录 rejected 及原因；明确告知未扣次 |
| 配额耗尽、截止时间已到、已有活动作业而拒绝 | 否 | 拒绝；不能排队到下个运行或突破截止时间 |
| 已计费作业的重复查询或重复投递 | 否 | 返回相同已保存结果，保持同一作业标识 |
| 同一内容再次主动提交为新作业 | 是 | 即使快照相同仍占新次数；内容摘要仅用于统计 |

基础设施重试必须保持候选快照、评测器版本、数据面板、seed、资源和时限不变。修改任何一项均不属于同一作业重试。客户端在首次网络请求前生成并保存稳定的 submission/idempotency key；服务端受理时原子化关联该键与 `evaluation_job_id`。即使 receipt 丢失，同键重试也返回已关联的原作业；同键不同快照拒绝。不得通过制造故障获取额外受保护反馈或多个随机结果后选最好一次。

### 5.2 必须分开的统计

| 字段 | 含义 |
|---|---|
| `feedback_budget_requested` | 运行配置中申请的最大配额 `n` |
| `submission_requests` | 所有提交请求，包括拒绝与幂等重复 |
| `feedback_jobs_counted` | 成功受理且占配额的作业数 |
| `feedback_jobs_completed` | 已生成持久终态结果的作业数，另按正常评分/候选失败/基础设施失败分类 |
| `feedback_jobs_delivered` | 开发截止前成功写入智能体可见工具结果的不同作业数 |
| `feedback_jobs_read_acknowledged` | 如代理具备确认机制，已明确确认读取的数量；否则 unknown |
| `distinct_artifact_hashes` | 已受理作业对应的不同内容摘要数量 |
| `evaluation_attempts` | 原执行及基础设施重试的总执行次数 |

“投递成功”只证明结果进入了智能体可见通道，不证明模型理解、使用或记住该反馈。旧 `collected_at` 可以作为查询行为证据，不能直接等同于认知上的“看过”。不同内容摘要也只表示内容发生变化，不能证明算法有实质创新。

默认反馈 schema 对每个任务固定，包括聚合指标、有效性、允许披露的约束诊断及截断规则。反馈粒度改变属于实验变量，需新的 `protocol_id`。禁止在日志、路径、异常文本或缓存中意外暴露密封输入和标签。

## 6. 候选选择、冻结与最终测试

### 6.1 默认选择政策

第一阶段采用原生最终产物方式：agent在T内将最终版本放在task.toml声明的artifacts路径，截止时收集并冻结该版本。agent可依据已计数反馈决定保留哪份代码，但框架不额外运行完整selection评分，也不在截止后代选最好checkpoint。没有修改时保留共同starter；最终文件损坏或缺失按预先固定的失败规则处理，不事后给某组补开发机会。

旧`best-public-selection / earliest-completed`仍存在于配置目录、模板和独立参考selector，保留为旧设计／第二阶段参考。它不等于第一阶段已经实现，也不要求为了新政策建设候选登记平台。正式批次须核对实际原生版本的artifacts收集、截止冻结和无修改路径。

### 6.2 冻结后执行

冻结发生在复核执行之前；第一阶段case本身已参与开发，不声称未见输入。冻结 artifact、依赖、入口点、训练 recipe、已训练权重、推理配置和随机状态；内容摘要写入 freeze receipt。最终评测在新的隔离工作目录执行该产物，每个实例/episode 按任务规则提供输入，并由独立 checker 重新验证输出与计分。

- **求解器任务**：运行冻结代码重新解决固定case；保存的静态答案不能代替实际算法执行。
- **ML 任务**：只使用冻结模型、已训练权重和允许的输入；主线权重只由公开 development 数据拟合，禁止用最终标签重新拟合。HEFTCom必须重新执行固定case的因果流水线生成bids，不能直接重放旧`bids.csv`。若允许按实例无标签适应，必须作为单独协议明确时间、状态和信息边界。
- **控制任务**：每个 episode 初始化状态；禁止从评测标签或其他算法评测中继承缓存。
- **输出验证**：以实际执行输出为准，独立重算物理/调度约束及目标值，不能相信候选自报分数。

第一阶段计数反馈与冻结复核使用**同case、同版本评分实现、约束、数值容差、指标、算法执行限额及资源合同**。第二阶段泛化才改用预先隔离的不同成员。具体面板与时限由 task release 固定，不能在看到候选后放宽或选择有利实例。构建、编译缓存、每实例重置、线程与训练权限必须在任务卡和产物契约中写明。

最终测试不占开发 `T` 和反馈 `n`，但受统一的最终评测资源与超时限制。默认每个冻结 run 只测一次 final-test；任务固有随机性所需的预注册评测 seed 列表作为一次完整测试面板执行。基础设施故障仅按原样重试，不能从多个有效最终成绩中挑最好一次。

观察到冻结复核结果后修复算法必须产生新研究批次，不能追加入原run。第一阶段本就明确case已参与自适应开发；第二阶段中旧测试应视作已暴露。正式测试集合数量有限时，应采用封存扩展或公开 validation/test 轮换策略，披露版本与曝光历史；不能无限反复声称相同测试“未见”。

## 7. 评分与失败分类

任务卡冻结原始指标、方向、有效性规则、实例聚合权重和基线映射。GOC 的官方软约束惩罚属于目标定义，不能为了追求“零违约”擅自重写评分。其他任务的硬约束按各自 checker 与数值容差判定。有效解、违反硬约束、带软惩罚的有效解必须可区分。

每个 run 同时保存原始目标值/收益/官方分数、有效性、资源成本、相对初始基线改进及任务内归一化指标。归一化映射必须来自已冻结的 task release；未证明最优的参考解不能标记为最优值。不得直接平均不同任务的 raw reward、货币收益和优化成本。

主结果先给出每个任务族及子设置的分布、均值/中位数、可行率和重复数。需要总指标时，先采用预注册的任务内映射，再按任务族等权或明示权重聚合；同时保留原始任务表。新增十个 GOC 实例不能使 GOC 在总分中自动获得十倍权重。

| 分类 | 例子 | 统计位置 |
|---|---|---|
| `valid-result` | 有效但性能低；按官方定义带软惩罚 | 正常算法结果 |
| `candidate-failure` | 求解器错误、超时、硬约束失败、输出格式错误 | 算法失败率与任务规定的失败分数 |
| `protocol-violation` | 使用禁止信息、超预算后继续修改、冻结产物不匹配 | 独立标记；不能纳入合规主比较 |
| `infrastructure-failure` | 评测器崩溃、存储/容器/模型服务故障、资源未能分配 | 基础设施失败率与缺失结果；不能伪装成有效零分 |
| `pending-or-unstarted` | 排队、未准备完成、任务尚未启动 | 批次覆盖情况；不当作已完成重复 |

既有超时/OOM不能只看外层作业标签：需要辨认是候选超出已分配资源，还是基础设施没有按声明供给资源。不能排除候选失败来只报告成功重复的均值；基础设施缺失也不能悄悄补成零分后掩盖故障。正式结果同时展示计划重复数、实际终态数、算法成功数和基础设施缺失数。

## 8. 恢复、公平性与重放

在同一运行中重启 judge 或执行器，恢复原账本、计数、快照和截止时间，不重新发放 `T`、`n` 或初始化一个“更好的”随机 seed。记录 `attempt_id`、重试原因、开始结束时间和版本。模型 API 重试不应重复已开始返回的响应，更不能悄悄产生两条分支再选优。

若因故障决定重新启动整个开发运行，使用新的 `run_id` 和 `cohort_id`，标记 `restarted-from-initial` 或 `resumed-from-checkpoint`。恢复候选不能与从头开发的候选冒充相同条件。需要新正式主比较时，对所有算法臂应用同一预注册重跑规则，并保留原失败记录；不依据已观察分数决定哪些臂值得重跑。

重放使用冻结 artifact、评测镜像摘要、评分实现、split 清单、seed 和资源 profile。重放是验证活动，单独留档，不新增“更好的主结果”。数值与随机任务需在 release 中规定容差或重复分布标准，不要求所有任务逐 bit 一致。

- [ ] 当前已暴露预实验面板标记为 calibration，并披露公共数据的暴露限制。
- [ ] 每个任务具有可运行初始基线和可信评分端独立checker、固定指标与容差；checker不提供给开发agent。
- [ ] 最终评测执行冻结算法；UC/SCUC 已完成从静态排程到求解器执行的迁移，HEFTCom 已完成从静态 bids 到预测与交易流水线执行的迁移。
