## 1. 为什么需要改版

原批次33次受保护反馈中，32次组合分为0。不是官方逐例目标F计算错误，而是本地面板聚合要求15例全部可行，否则整组归零；同时，可行实例的目标质量只在全板可行时才返回。不同程度的进步被压成相同标量，信息难以用于搜索。

两个求解时限的角色也需要统一。原生任务指标、ABC评测助手和保护反馈围绕900秒；5400秒已向agent披露，但只是冻结后的独立重评。此前n=0暂时领先的是5400秒质量分。已有900秒结果全部被全板门槛记零，n=0平均可行10.5/15例，n=3、n=5已有结果各14/15例。不能据此得出反馈有害，也不能把90分钟质量排序当作15分钟演化能力排序。详见[历史轨迹分析](../experiments/rte-feedback-trajectory-analysis-20261017.md)。

## 3. 面板排行：可行例数优先

**用户已确认采用本节规则。** 不再用全板一票否决抹去主指标差异，按以下二元组从高到低排列：

1. 可行例数k，范围0–15。
2. 固定分母质量Q：15例归一化质量之和除以15；无效例贡献0。

逐例有效质量q继续使用现有输入尺度s与固定映射：`q = 0.5 - atan(F/s)/pi`，实现保留现有数值稳定分支；s来自输入而非参赛方法的最好成绩。无效实例在反馈中的F、风险分解及q均为null，汇总时质量贡献0，不能伪造一个“无效目标值”。

同等可行数比较Q，可以区分质量改进；固定15例分母避免把“仅成功的子集均分”误当整板性能。**一个额外可行实例优先于任何质量改进**，这是明确的研究取舍，而非官方竞赛规则。全部15例可行时，Q就是原全板有效质量均值。

如框架必须接收单个标量，可用 `reward = (k + Q) / 16` 编码这一顺序。由于每例q在[0,1]内、Q按固定15例计算，少于15例可行时Q严格小于1；任意增加一例可行都优先于原来所有质量变化，同等k时则随Q增加。v2原生指标名统一为`rte_x15_coverage_quality_900_v2`；部署时应统一指标声明、反馈与最终900秒记录。这个标量仅是排序编码，不是官方F或原赛积分；不能与v1归一化分数直接比较。

同时单列`all_cases_feasible`，以识别真正达到15/15的求解器。v2允许部分可行候选按上述二元组比较，不再以全板门槛抹去差异；某个失败实例仍然没有有效官方目标。原赛积分及历史全板门槛另列，不与v2混称同一规则。

## 4. 每次反馈应该告诉agent什么

通过原框架已有`feedback`字段返回有版本号的结构化JSON，不新增网关、评分服务或恢复框架。完整私有`details`继续留在评测端。

| 层级 | 返回字段 | 用途与边界 |
|---|---|---|
| 面板 | schema版本、候选摘要、900秒预算、15例数量、评测是否完整完成 | 确认是哪一版代码、哪种预算，区分算法失败与评测服务失败 |
| 汇总 | k、可行比例、Q、排序标量、是否15/15、状态计数、约束错误计数 | 让可行性与质量分别可见，避免仅看一个总分 |
| 每例 | 稳定实例ID、AC／WA／RE／TLE状态、candidate退出码 | 定位哪类实例及哪种执行问题发生变化 |
| 有效例 | 官方F、mean_risk、expected_excess、q | 即使其他实例失败也照常返回，区分均值风险与超额风险的取舍 |
| 无效例 | F、风险及q字段为null；固定类别的约束错误计数 | 约束错误、无输出、运行退出和超时分别保留；不把不可行输出算成有效目标 |
| 执行诊断 | 候选墙钟、候选子进程峰值RSS及明确单位 | 识别解析／建模成本和资源取舍；不将RSS误称容器总内存峰值 |

**反馈不是只有一个得分。** 例如下面三行是人工示意，展示同一次反馈如何帮助定位问题，不对应真实X结果：

| 实例 | 状态 | 目标与诊断 |
|---|---|---|
| X_01 | AC | 返回该例F、均值风险、超额风险、q、耗时及RSS；可与agent自己保存的上次反馈比较 |
| X_02 | TLE | F为null；返回候选墙钟、RSS与超时状态，提醒算法需要控制900秒总执行成本 |
| X_03 | WA | F为null；例如`resource_upper: 3`，表示检测到3项资源上界错误，而非一个无法解释的0分 |

实际反馈必须覆盖完整15例，不只显示上述节选；汇总与逐例记录须对得上。框架无需保存另一套“上次最优”状态，agent直接比较自己已获得的反馈即可。公开仓库继续只发布真实实验的聚合统计；上述逐例诊断仅在实验中经计n接口提供给该次开发agent。

第一版只暴露现有记录中已可靠算出的诊断。checker目前支持的格式、资源上下界和exclusion错误计数可以直接复用；不承诺尚未实现的违反幅度、精确失败行或solver内部失败原因。RE退出码不能单独证明发生OOM，应以可信资源记录另行审计。

只返回白名单数值、固定分类和实例ID；不返回X输入、解文件、原始stdout/stderr、checker原文、主机路径或私有轨迹。整板完成后一次性回传，控制在原框架16 KiB反馈上限内；超限应在发布前校验，而不是截断成损坏JSON。逐例诊断会增加每次反馈的信息量，必须对所有n>0组保持同一版本，且仍只通过计数评分器获得。

某次已完成面板可能只有部分有效候选；这与基础设施没有完成评测不同。后一种情况应明确记录错误，不能伪装成15例算法失败或可用的零分。受理计n及失败处理沿用冻结的统一记账政策，不增加隐性免费重试。

## 5. agent题面与最终选择

题面应明确：优化900秒表现；5400秒仅作扩展观察；ABC工具与保护反馈均围绕主时限。评分公式、尺度确定方法、候选输入接口、失败规则和反馈字段在开发前一致说明，X原始数值输入仍留在评测端。

还应明确最终提交是截止工作区。agent可以自行保存受过验证的版本、安排反馈时间并选择最终版本；框架不会自动把它替换成历史最高分。是否采用“保留最后一次反馈接近截止”等策略属于后续agent设计消融，不静默写进某一个n组。
