# 决定 0004：复用 eval-in-loop，只做个人小规模测试必需工作

**状态：按用户要求采纳。日期：2026-10-15。** 本决定收缩个人侧的后续开发范围；平台能力由后端维护。目标是用已有框架测试能源 task 和研究想法。

## 1. 默认运行路线

**现有 eval-in-loop + 已有 task 包 + 原生配置／启动／结果文件。**

原框架已经提供任务模板、Harbor 环境与 agent 执行、配置与启动、运行中反馈、账本、提交快照、续跑和状态查询。直接复用这些能力。原来能跑的任务入口和模型连接方式优先沿用。

“薄层”首先是配置约定、任务文件和检查说明；当前不要求新增一个运行服务或公共 Python 中间层。确有阻断时，优先调整配置或修正原 task／原适配点。

## 2. 个人侧只保留三项工作

| 工作 | 最小内容 | 完成标准 |
|---|---|---|
| 任务可运行 | 复用原 task 的题面、环境、算法入口、数据、checker 和 starter；只补实际缺失的文件、依赖或执行适配 | starter 能运行，输出能被原 checker 正确评分 |
| 实验配置 | 使用原框架支持的 task、模式、模型、T、n、资源、seed／重复及输出目录；实际值单独决定 | 配置足够启动本次实验，关键设置有记录 |
| 检查与记录 | 使用现有日志、反馈记录、评分与导出产物；必要时人工整理 Markdown／CSV | 能解释本次是否跑完、得到什么结果、失败在哪里 |

不要求为一次小测填写独立参考实现的全部 49 个字段、生成正式 task certificate，或实现新的通用报告管线。

`n=0` 使用现有 `terminal` 模式；需要受控反馈时使用对应 in-loop 模式和正数评测预算。judge 内部 `0=unlimited` 需要正确映射模式，并不表示框架缺少零反馈能力。具体参数名沿用实际使用版本。

算法入口、checker、数据和基线分别复用五个任务的既有实现。GOC 的数值桥、UC 的求解与核验、RTE 官方 checker、L2RPN 仿真与 scorer、HEFTCom 预测／结算代码不重新开发一套。某个旧 grader 只验证静态答案时，可用于对应调试；要比较算法处理新输入的能力时，才在该 task 内补齐必要执行入口并核验结果。

## 3. 什么时候允许增加代码

只有出现具体问题时才处理：

1. **启动不了或中途无法继续：** 缺文件、缺依赖、实际 API／模型协议不兼容、任务入口错误。
2. **无法得到正确结果：** checker 调用错误、没有执行应执行的算法、分数或产物丢失、数据／预算配置明显不符。
3. **已经观察到同一问题反复影响小测：** 先定位责任，再决定最小修复；平台问题交由后端维护或协作接入现有修复。

每次补丁都需说明“哪个实际运行因此失败或结果错误”，优先配置修改，其次 task 内局部修复；只有修复实际代码时才增加对应的必要回归检查。当前不因未来可能需要而提取新框架模块。

## 4. 从个人开发清单移出的内容

| 内容 | 当前处理 |
|---|---|
| 新 Lifecycle／Clock／Ledger／Artifact Store／broker | 不继续扩建，也不要求五任务迁入；优先复用原框架 |
| 新模型网关、调度器、跨节点存储与通用恢复系统 | 使用已有能力，平台问题由后端维护／协作处理 |
| 完整 ACK／幂等协议、故障注入矩阵与会话／Pod 自动恢复 | 不作为个人小测前置；出现实际阻断再针对处理 |
| 目标并发压力、恶意代码逃逸与生产认证 | 留作后端或后续正式发布的独立工作 |
| 额外配置框架、证书服务、排行榜服务、通用统计平台 | 当前不建设；原生配置和结果文件足够时直接使用 |

已有 `powergrid_bench` 代码、测试、文档和 RTE canary 证据保留为参考与历史记录。RTE 已通过的 canary 实际使用了新内核接桥；**本决定没有把该作业改写为原生路径，也没有执行回迁或删除代码。** 后续个人小测以原框架可运行入口为起点，逐任务核对实际使用路径。

## 5. 小测的最低检查与报告

先使用已有 task 检查和 starter／oracle 路径确认输入、环境、输出与评分；已有同版本证据可直接复用。随后按本次要研究的模式做一次小规模真实模型测试，核对模型调用、正常结束或明确失败、评分和导出产物。用到反馈时，额外核对实际受理／取回次数与配置；异常如实记录，不能以作业显示成功代替评分成功。

保留：task／数据范围、代码版本、模型、T／n／资源／seed、运行 ID、最终产物、原始分数／有效性和失败原因。优先读取现有记录；用量未知记 unknown，不补造数字。补跑保留原运行关系和失败，不自动升级为中断恢复成功。

小测可以在低并发下逐个 task 推进，无需等待五任务全部完成生产认证、跨节点 WAL 或完整故障演练。当前已有 RTE 的真实主链路证据，其余四任务已有旧任务实现与预实验记录；先检查能否直接复用，只处理实际缺口。

## 6. 保留研究协议，明确小测结果的用途

减少工程不等于放宽结果解释：原始分数、算法失败和基础设施失败仍需分清；历史公开数据继续标为 calibration。相同方法比较记录相同预算、资源、数据和评分条件；不能把不同 task 的 raw 分数直接平均。

既有研究合同中的四角色、`best-public-selection`、无累计 token cap、冻结算法终评等没有被静默改写。原生 task 若使用不同选择方式、重复使用反馈／最终面板、仅评分静态答案，需记录为 **calibration／protocol variant**，不能直接纳入原合同下的正式比较。若某项研究确实依赖这些保证，再决定使用后端已有能力或最小 task 修改。

完整 benchmark release、原赛公平排行和论文结论仍需对应证据；这些要求作为未来研究／发布参考，不自动变成当前个人侧的开发任务。

## 7. 后续执行顺序

1. 列出五个已有 task 的实际入口、最少配置、checker、输出位置和已知阻断；能跑的直接复用。
2. 对本次要用的 task 做最低检查；失败时只修具体问题，不扩展成通用平台。
3. 用原框架提交小规模实验，保存原始结果和简短中文记录；再据结果决定是否需要下一项修改。
