# Benchmark 研究契约与任务范围

> **当前第一阶段政策（2026-10-15）：以[决定0005](decisions/0005-fixed-case-evolution-first.md)为准。** 每task固定一个高难完整case，同case开发、计n反馈与冻结复核；开发端禁止完整checker和本地完整目标评分，不设免费public-selection。下文四角色／独立留出、公开checker、best-public-selection等属于较早设计或第二阶段参考，不是本阶段默认。原生入口的实现与验收状态见当前决定和各任务卡§12。

**版本：`v0.1-design`；日期：2026-10-14；状态：前两步文档规范完成，运行能力待实现与认证。**

本规格把前期多组实验转为后续研究共同遵守的契约。已有实验事实见[预实验统计](evidence/preliminary-experiments-20261013.md)，执行细则见[评测协议](protocol/evaluation-protocol.md)，提交与留档见[产物契约](protocol/artifact-contract.md)。本文的要求是正式 release 的验收条件；本次发布没有完成运行框架修复或新实验。

## 1. 最终目的与研究对象

构建约五个能源领域优化/ML 任务族，以及一套可稳定批量运行的 eval-in-loop 算法演化框架。智能体在公开上下文和统一资源条件下开发算法，通过有限受保护评测改进，最终提交冻结的代码与必要权重。研究的问题是智能体与演化机制能否提高算法质量、可靠性和泛化，而不是只获得某个已知实例的高分答案。

主要科学产物包括：可复现任务发布、受控反馈协议、可重放的算法产物和运行记录、方法/消融结果。前期观察用于发现问题和校准难度；不能直接升级为框架有效性的论文证据。

## 3. 五个任务族的选择与覆盖

| ID / 任务卡 | 主要能力与研究价值 | 核心范围 | 扩展范围 |
|---|---|---|---|
| [goc-sc-ac-opf](task-cards/goc-sc-ac-opf.md) | 非凸数值优化、故障分解、物理可行性、工程并行 | GOC Challenge 1 中可完成常规矩阵的中等规模 SC-AC-OPF | GOC30000 大规模压力、不同规模/拓扑档位 |
| [unit-commitment](task-cards/unit-commitment.md) | MILP、离散/连续耦合、约束建模与启发式求解 | 标准 UC 通用求解器 | 清晰标注模型限制的 SCUC 适配 |
| [rte-maintenance](task-cards/rte-maintenance.md) | 资源受限组合排程、风险目标、局部搜索 | ROADEF 2020 检修排程通用算法 | 更大规模与不同约束模式 |
| [l2rpn-grid-control](task-cards/l2rpn-grid-control.md) | 规则/RL/仿真搜索、序贯物理决策 | 一个锁定环境下的时间/场景泛化 | 多拓扑、GPU 训练、在线 LLM 控制独立协议 |
| [heftcom-forecast-trade](task-cards/heftcom-forecast-trade.md) | 时间序列 ML、特征设计、预测到报价的收益优化 | 固定历史离线回测，冻结预测/交易管线 | 滚动重训、在线适应或实时数据独立协议 |

选择依据：能源相关性明确；有公共问题定义/数据入口；能够运行冻结算法并独立检查输出；覆盖互补的连续、离散、序贯和预测决策能力；已有预实验可以发现真实工程缺口；有可校准的基础与较强基线。五家族均为**已选定建设对象、尚未通过运行认证**。

任务数量按家族统计，不按母线数、n 条件或重复计数。UC 与 SCUC 属于同一家族，但模型、数据和难度分别记录，不能把受限 DC 线路安全适配描述为完整官方 SCUC。AHC024 不属于能源 Benchmark，保留为框架超时、失败和批次报告测试。[范围决定](decisions/0001-benchmark-scope.md)保存这些边界及替代条件。

## 4. 研究问题与可检验主张

| 研究问题 | 改变的变量 | 必须控制的条件 | 能回答什么 / 不能直接回答什么 |
|---|---|---|---|
| R1：受保护反馈预算有什么作用？ | n；或独立的反馈粒度协议 | 同一任务、模型、资源、T、selection、基线与恢复规则 | 固定墙钟下反馈策略的综合作用；含等待成本，不能解释为不受时间影响的纯信息效应 |
| R2：智能体组织如何影响结果？ | 单/多智能体、角色协作、记忆、工具规划 | 总资源和总 n 共享，模型政策与 T 相同 | 组织机制的表现与可靠性；不能把额外计算资源算成结构优势 |
| R3：演化机制如何影响结果？ | 人口、变异、候选选择、归档、探索策略 | 共同初始候选、数据角色、总预算与最终选择规则 | 机制改动的任务内效果与跨家族稳健性 |
| R4：开发改进能否泛化？ | 方法；预注册的时间或跨拓扑 split | 完全独立的最终面板、冻结算法、一致评分 | 开发/选择/反馈到终评的差距；固定已知实例高分不能代替泛化 |
| R5：框架稳定性是否足以支持研究？ | 版本或修复前后的认证批次 | 相同验收样本与故障处理；历史/恢复批次分开 | 运行成功率、账本一致性和可重放率；不能只报告最好成功例 |

先完成 R5 的发布门槛，再开始 R1/R2/R3 的正式方法结论。实验同时保留合法零分、候选失败、协议违规与基础设施缺失，具体规则见评测协议。

## 5. 统一词汇与实验单位

| 名称 | 含义 |
|---|---|
| task family | 一类问题与演化目标，如 GOC 或 L2RPN；用于跨任务宏平均 |
| task release | 具体数据、约束、scorer、接口、依赖、资源、预算、baseline 和切分的冻结组合 |
| instance / episode | 算法处理的一份输入或完整控制场景；不是独立开发重复 |
| candidate / artifact | 开发中一份可执行算法内容快照；源码、配置、权重都影响身份 |
| evaluation job / attempt | 一个被受理的评测作业，以及原执行/原样重试的执行尝试 |
| run | 一次开发过程及其最终冻结算法，具有独立 run_id 和 seed |
| cohort | 相同预算、协议、模型与恢复条件的可比较运行组 |
| slot | 预先计划的一格实验；未启动、失败与补跑关系均保留 |

原始 98 个槽位横跨多种旧协议。不同预算、切分、静态/执行评测、恢复来源的 run 不能因为名字相近就合并。

## 6. 数据与信息边界

每个正式任务有公开开发、公开选择、受保护反馈、最终测试四角色。旧预实验用过的面板和成本试测样本标记 calibration，不能重新声称未暴露。先识别同源实例/时间窗口/拓扑关系，再按研究主张分组切分；跨拓扑与同拓扑时间泛化分开发布。

公开目标、合法 checker、公开训练标签和允许的环境模拟可以使用。n 限制的是受保护面板的服务端评测作业；如果同一面板输入与目标已完整可见，本地计算不可能被包装成真正受限的信息访问。保护依靠数据和执行权限隔离，并审计异常日志、缓存、出网与未来信息。

公共历史数据可能已经进入模型预训练或外部知识，访问隔离不保证从未见过。最终 claim 必须披露数据公开性、暴露历史和实际隔离措施；需要更强新数据时另行构建任务版本。

默认训练使用 public-development 的合法标签；public-selection 用于选择，不加入主线模型拟合。允许利用 selection 标签重拟合的设置须另立协议，并在 T 内完成、重新验证/冻结产物；不能在终评后补训练。具体时间切分与拟合规则在 HEFTCom 卡片中保存。

## 7. 预算、资源与默认实验设计

共同开发预算为墙钟 T。统一环境准备结束后启动时钟；模型请求、工具、训练、编译、本地检查、公开选择、受保护评测等待均在 T 内。所有代理共享预算。冻结后的最终评测单独限时，不能增加开发机会。**累计 token 只记录、不封顶、不预留、不触发停止**；单响应上限、上下文与 provider 限流另行声明。

每个 release 分别固定开发、受保护反馈、最终构建/执行的 CPU、RAM、GPU、线程、磁盘、网络、缓存和超时。任务间可采用不同 T 与资源；任务内被比较的方法必须采用同一已声明 profile。固定墙钟与资源不意味着工作量或成本完全相同，报告实际耗时与 token。

初步研究矩阵采用 n ∈ {0,1,3,5}；n=20 是成本校准后决定的扩展条件，当前不把它写成强制正式预算。没有填实资源/超时的设计清单不得发起正式实验。不限次数如用于研究，必须有独立 budget mode 和 protocol_id，不能以 n=0 表示。

校准批次可采用 3 个独立开发 seed 估计失败率与方差；正式主比较以至少 5 个独立开发 seed 为建设目标，是否足够应按校准方差、效应大小与成本预注册。不能把同一产物测多周或多次推理当作更多独立开发重复。开发 seed 与评测随机 seed 分开记录。

优先用配对任务输入、评测 seed 和开发 seed 比较方法。先跑简单基线和传统强基线，再跑 n 消融，最后做结构消融；避免第一批即展开五任务×多模型×多结构×多 n 的巨大矩阵。资源与模型允许集未冻结前不作正式排行榜。

## 8. 评分、统计与结论规则

每个 release 先固定原始指标、方向、硬约束/软惩罚、数值容差、逐实例聚合和失败分数，再校准基线。主要指标包括：最终算法质量、有效/可行比例、合法零分与候选失败率；同时报告开发成本、评测耗时、峰值资源、实际反馈数和基础设施缺失。

任务内可用相对基线改进作为共同展示形式：最小化且基线 B>0 时 `(B−C)/B`，最大化且基线绝对值非零时 `(C−B)/|B|`。它们是可选映射示例；基线接近零、负收益或含失败处罚时需另定稳定映射并冻结。参考解未证明最优，不能把相对参考差写成 optimality gap。SCUC 的约 10⁻⁷ 变化必须先经过数值容差与实质改善阈值检验。

跨家族总指标须采用预注册任务内映射，并按五家族等权宏平均或明确理由的固定权重；新增某家族实例不自动增加其权重。本次未计算跨任务总分，因为尺度、预算与数据协议不一致。

正式结果以 run 为开发统计单位，保留每实例/episode 的明细及分组关系。报告计划 run 数、实际终态数、候选有效数、基础设施缺失数，以及均值、标准差、中位数和不确定性区间。配对方法差值优先；时间场景按块分析，不能把相关半小时/控制步当独立样本。区间构造和检验方法在校准后预注册，不能根据显著性选方法。多条件探索标记 exploratory；主要假设和多重比较处理提前声明。

候选失败按任务发布的失败规则进入算法性能/成功率；基础设施失败作为缺失并报告，采用分数不可知的统一重跑规则。只给成功 run 均值时必须同时给全计划成功率，不能悄悄删除合法零分或失败。恢复开发与从头开发单独 cohort；最好的中间分数不能替代失败运行的正式终评。

## 9. 通用框架边界

任务层负责数据角色、物理/业务定义、输入输出、独立 checker、基线与评分。开发框架负责模型调用、agent 组织、候选演化、本地工具与公开 selection。协调评测层负责共同计时、受保护接口、受理/投递账本、不可变快照、截止冻结、最终执行和结果记录。

统一的是生命周期和记录语义，算法接口允许保留各任务合适的语言与文件形式。最终输入必须执行算法，独立重算输出指标。模型 provider 版本与私有服务连接留在开发层；正式求解器默认不调用外部 LLM，不把受保护输入传给外部服务。

框架故障不能被 task 自报分数掩盖；task 无效输出不能被解释为平台缺失。所有状态可映射到 valid-result、candidate-failure、protocol-violation、infrastructure-failure、pending-or-unstarted。

## 10. 版本、公开性与发布门槛

设计版本不具备正式 release 的可运行保证。数据、模型、scorer、容差、切分、接口、资源、预算、selection、反馈 schema 或恢复规则改变时，产生可辨认的新任务/协议版本。历史 manifest 不重写；新证据追加带日期快照。

正式 release 必须具有真实且审计通过的切分清单、许可和来源、不可变代码/数据/环境摘要、可运行基线、资源校准、契约验收、目标并发批次与重放证据。全部条件见[实施与验收矩阵](implementation-plan.md)。若某家族无法提供合理成本、可靠 baseline 或可信留出，应保留诊断记录，缩小其研究主张或替换，而不是为凑齐五类放宽要求。

本次公开中文设计与脱敏预实验事实。未核验的原始数据、私有框架代码、原始轨迹和集群配置不随文档上传；外部读者当前无法独立重算内部历史成绩。正式方法结论应使用另外发布的可复现产物。
